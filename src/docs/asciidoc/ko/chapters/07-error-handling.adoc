== 오류 처리 (Error Handling)

hg4j의 checked-exception 계층은 의도적으로 이렇게 설계했습니다. 흔히 기대하는 것과 달리 모든
예외가 `IOException` 하나로 모이지는 않습니다.

[cols="1,1,3"]
|===
|예외 |상속 관계 |발생 시점

|`HgLockException`
|`HgException` (`IOException`이 아님)
|`.hg/wlock` 또는 `.hg/store/lock` OS 레벨 파일 락을 잡지 못했을 때. 다른 프로세스나 다른 `Hg`
인스턴스가 지금 저장소에 쓰는 중이라는 뜻입니다.

|`HgMergeConflictException`
|`HgException` (`IOException`이 아님)
|`GraftCommand`, `BackoutCommand`, `RebaseCommand`가 내부 cherry-pick/replay 머지 과정에서
하나 이상의 파일을 미해결 충돌 상태로 남겼을 때.

|`HgRepositoryNotFoundException`, `HgRevisionNotFoundException`, `HgValidationException`,
`HgTransportException`, `HgCorruptDataException`, `HgCensoredContentException`
|`IOException`
|그 외 대부분: 저장소를 찾을 수 없거나, 리비전 문자열을 해석할 수 없거나, 잘못된 입력이거나,
네트워크/와이어 프로토콜 오류이거나, 디스크상 데이터가 손상/censor된 경우.
|===

`HgLockException`과 `HgMergeConflictException`은 `IOException`의 하위 타입이 **아닙니다**.
그래서 `catch (IOException e)` 하나만 걸어두면 이 둘은 조용히 그대로 빠져나갑니다. 대부분의
커맨드 메서드가 `throws` 절에 이 둘을 따로 명시해 두는 이유도 여기에 있습니다. 락 경합과 일반
I/O 실패를 다르게 처리해야 한다면 각각 catch하세요.
