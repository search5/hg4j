== Work in Progress: Shelving & Worktrees

This chapter covers `shelve()`, which sets aside work you don't want to commit yet;
`worktree()`, which creates another working tree sharing the same repository; and `resolve()`,
which clears conflicts left behind by a merge, graft, rebase, or backout.

=== Setting changes aside (shelve)

[source,java]

`shelve()` saves the working tree's currently modified/added/removed files under a given name,
then reverts the working tree back to its parent commit. This lets you clear your workspace
without committing when you need to switch to something else urgently. Omitting `setName()`
leaves the name at its default, `"default"`.

=== Restoring shelved changes (unshelve)

[source,java]
----
include::{examplesdir}/WorkInProgressExamples.java[tag=unshelve-changes]
----

Passing `setUnshelve(true)` does the reverse. Internally, the shelved changes are replayed as a
throwaway commit on top of the parent they were originally shelved from; if the working tree's
parent has since changed (because something else was committed on top of it), that throwaway
commit is rebased onto the new parent -- a no-op if nothing happened in between -- and the result
is finally released back onto the working tree as pending, uncommitted changes. The throwaway
commit created along the way is erased without a trace the moment this succeeds.

If the rebase step hits a conflict, it pauses exactly the way a real `hg rebase` would, and an
`HgMergeConflictException` is thrown. Once you've resolved the conflicting files (see "Resolving
conflicts" below), call `unshelveContinue()` to proceed, or `unshelveAbort()` to give up on this
attempt while leaving the shelve itself intact for a later attempt. Both methods rely purely on
state persisted to disk rather than anything held by this instance, so it's fine to call them on
a freshly obtained `ShelveCommand`.

`worktree()` is just a more Git-familiar name for what is really Mercurial's `hg share` --
rather than creating an entirely separate repository, it creates a new working tree that shares
the **same store**. A commit made from either working tree is immediately visible from the
other. The return value is an `HgRepository` pointing at the new working tree, and the target
directory must be empty or not yet exist.

=== Resolving conflicts

[source,java]
----

----

`resolve()` inspects and updates the conflict state left behind by `merge()` (see
<<branches-bookmarks>>) or by `graft()`/`rebase()`/`backout()` throwing
`HgMergeConflictException` (see <<error-handling>>). All of these commands share the same
`.hg/merge/state2` file, so `resolve()` can inspect or clear a conflict left by any of them.
`list(true)` returns the resolution state of every file involved in the current merge, and
`setFile(path).markResolved(true)` marks a single file -- whose `<<<<<<< / ======= / >>>>>>>`
markers have been cleaned up by hand (or by some other tool) -- as resolved. An exception is
thrown if no merge is in progress, or if the given file isn't part of the current merge.
