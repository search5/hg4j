== 1. 소개
`hg4j`는 **Mercurial (hg) SCM**을 순수 자바로 구현한 라이브러리입니다. **JGit**의 분리된 설계를 따라서, 저장소 형식을 읽고 쓰는 배관(plumbing) 계층과 그 위의 명령 객체(porcelain) 계층으로 나뉩니다.

모든 동작의 기준은 실제 Mercurial입니다. 같은 시나리오를 hg4j와 실제 `hg`로 각각 실행해서 저장소, 출력, 종료 코드를 비교하는 방식으로, `hg` 7.2(순수 Python), Rust 빌드 7.2.4, 같은 계열의 개발판에 맞춰 검증합니다. 이전 Mercurial 릴리스는 테스트 매트릭스에 들어 있지 않습니다. <<known-issues>>를 참고하십시오.

이 문서는 구조, 명령 목록, 잠금과 트랜잭션 규칙, 지원하는 저장소 형식, `hg`와 의도적으로 다른 부분, 알려진 문제를 설명합니다.

== 2. 핵심 구조
=== 2.1 배관 API
* **`HgRepository`**: `.hg/` 배치를 총괄합니다. 작업 사본 잠금(`wlock`)과 저장소 잠금(`lock`)을 잡고, revlog를 열고, dirstate 컨텍스트(<<dirstate-contexts>>)를 소유하며, 잠금이 풀린 뒤로 미룬 작업(`afterLock`)을 실행합니다.
* **`Dirstate`**: 작업 사본의 상태입니다. dirstate-v1과 dirstate-v2를 읽습니다. v2 파일은 메모리에 매핑해서 제자리에서 조회하고, 바뀐 항목은 덮어쓰기 계층에 두었다가 원본처럼 데이터 파일 끝에 덧붙여 씁니다(<<dirstate-storage>>).
* **`Revlog`**: 인덱스(`.i`)와 데이터(`.d`) 파일, inline과 분리 저장, generaldelta, revlog-v2(docket), sidedata를 갖는 changelog-v2를 다룹니다. 압축은 zlib과 zstd를 지원합니다.
* **`TreeWalk`, `ChangesetGraph`**: 매니페스트와 작업 사본(`treewalk` 패키지), 리비전 그래프(`revwalk` 패키지)를 순회합니다. `RevWalk`라는 이름의 클래스는 없으며, 리비전 그래프는 `ChangesetGraph`, `RevFilter`, `SortOrder`로 순회합니다.
* **`match`, `fileset` 패키지**: 패턴 매처(`path:`, `glob:`, `re:`, `rootfilesin:` 등), 파일셋 언어(파서, 분석, 최적화, 술어 24종), 명령들이 함께 쓰는 `-I`, `-X`, `set:` 선택을 제공합니다.

==== 클래스별 계약
각 항목은 Javadoc이 약속하는 내용입니다. "잠금"은 호출자가 이미 쥐고 있어야 하는 잠금을 뜻하며, 배관 클래스는 명시된 곳에서만 이를 검사합니다.

`Repository`, `HgRepository` (`lib` 패키지)::
* `Repository.open(File)`은 `HgRepository`를 반환하며 `.hg` 디렉터리가 없으면 `HgRepositoryNotFoundException`을 던집니다. `new HgRepository(File)`은 `requires`를 읽고, 읽기 오류는 무시한 채 기본값을 남깁니다.
* 스레드 안전성: 클래스 Javadoc은 병렬 읽기에 안전하다고 설명하며, 대부분의 메서드가 `synchronized`입니다. 잠금 메서드 `lockWorkingCopy`와 `lockStore`는 일부러 `synchronized`가 아닙니다. 잠금을 기다리는 스레드가 객체의 다른 메서드를 막지 않게 하기 위해서입니다.
* `getDirstate()`는 잠금을 잡지 않으며, 현재 스레드에 변경 컨텍스트가 열려 있지 않으면 호출할 때마다 파일을 읽습니다. 열려 있으면 컨텍스트의 인스턴스를 돌려줍니다. `writeDirstate(Dirstate)`는 컨텍스트가 없으면 즉시 쓰고, 있으면 가장 바깥 컨텍스트가 정상적으로 끝날 때 쓰도록 표시만 합니다. 호출자는 `wlock`을 쥐고 있어야 합니다.
* `getRevlog(idx, dat)`는 인덱스 파일의 정규 경로로 revlog를 캐시하므로(최대 100개, 가장 오래 쓰지 않은 것부터 버립니다) 반복 호출하면 같은 객체를 돌려줍니다. 저장소가 객체 몰래 바뀌었다면 `clearRevlogCache()`를 호출하십시오. `refreshIfChangedOnDisk()`는 오래 열어 둔 핸들을 위해 `00changelog.i`가 바뀌었고 캐시된 changelog가 로컬에서 쓴 적이 없을 때 이를 대신 수행합니다.
* `getPhaseRoots()`는 그 시점에 `.hg/store/phaseroots`를 읽은 새 `PhaseRoots`를 돌려줍니다.
* `getRequirements()`는 `.hg/requires`와 `.hg/store/requires`의 합집합을 돌려줍니다.

`HgLock` (`lib` 패키지)::
* 원자적으로 만드는 잠금 파일입니다(POSIX에서는 심볼릭 링크, 그 밖에서는 새로 만드는 파일). JVM 안에서 경로 기준으로 추적하므로 다른 스레드와 실제 `hg`를 모두 배제합니다. `close()`로 풀며, 같은 인스턴스를 두 번 닫아도 아무 일도 일어나지 않습니다.
* 이미 잠금을 쥔 스레드가 다시 잡으면 성공하고(`isReentrant()`가 `true`) 한 단계를 더 셉니다. 마지막 단계가 닫힐 때 파일이 지워집니다. `HgLock(File)`은 즉시 실패하고 `HgLock(File, timeoutMs)`는 그 시간만큼 기다립니다.
* `HgRepository`의 `afterLock` 작업은 그 저장소에서 스레드가 쥔 마지막 잠금이 닫힐 때 한 번 실행되며, 쥔 잠금이 없으면 즉시 실행됩니다. 실패한 작업은 기록만 하고 던지지 않습니다.
* `HgLock.noOp()`은 아무것도 하지 않는 잠금입니다.

`NodeId` (`lib` 패키지)::
* 변경할 수 없는 20바이트 노드 id입니다. 생성자와 `getBytes()`는 배열을 복사합니다. `NodeId.NULL`은 0바이트 20개이고, `fromHex`는 정확히 16진수 40자리를 요구합니다. `toString()`은 앞 12자리만 돌려주므로 전체 id는 `toHex()`를 쓰십시오.

`ProgressMonitor` (`lib` 패키지)::
* `start(title, totalWork)`(`UNKNOWN` = -1), 이어서 직전 호출 이후에 끝난 작업량(누적값이 아님)을 넘기는 `update(completed)`, 마지막으로 `end()`를 호출합니다. 오래 걸리는 작업은 `isCancelled()`를 확인해 일찍 멈춥니다. `message(String)`은 재정의하지 않으면 무시됩니다.

`Dirstate` (`dirstate` 패키지)::
* 잠금: 읽기와 쓰기 모두 잠금을 잡지 않습니다. `wlock`을 쥐고 쓰십시오(`changingFiles`, `changingParents` 안에서는 `HgRepository`가 끝에서 `write`를 한 번 호출합니다).
* `addEntry`, `removeEntry`, `addCopy`, `setParents`, `setV2`와 `getEntries()`, `getCopyMap()`(둘 다 살아 있는 맵을 돌려줍니다)을 통한 모든 변경은 `write(File)` 전까지 메모리에만 있습니다.
* `read(File)`은 v2 데이터 파일을 읽기 전용으로 매핑해 제자리에서 씁니다. 그 파일을 읽을 수 없으면 `getEntries()`를 통한 조회가 `UncheckedIOException`을 던질 수 있습니다. `read(byte[])`는 v1만 해석하며 복사 맵을 먼저 비우지 않습니다.
* v1의 `write(File)`은 파일을 원자적으로 교체합니다. v2는 변경분을 데이터 파일에 덧붙인 뒤 docket을 원자적으로 교체합니다. 디스크의 파일이 읽었던 것과 달라졌거나 데이터 파일의 절반 이상이 도달할 수 없으면 새 데이터 파일(새 uid)을 쓰고 이전 것을 지웁니다.
* `serialize()`는 항상 v1 형태를 돌려주며 나노초 부분은 저장하지 않습니다. `DirstateV2Serializer.serialize`는 데이터 파일만 만듭니다(docket과 복사 기록 없음). 완전한 v2 dirstate는 `Dirstate.write`로 얻습니다. `DirstateV2Node`는 `ByteBuffer` 위의 고정 44바이트 노드 배치이고, `LazyEntryMap`은 패키지 전용이며 `getEntries()`로만 접근합니다.
* `Dirstate.Entry`는 변경할 수 없는 레코드입니다. `time`은 0부터 `0xFFFFFFFF`까지여야 하며(`AMBIGUOUS_TIME`은 믿을 수 없는 mtime), 음수 `size`는 "내용을 비교하라"는 뜻입니다(`isStatAmbiguous()`).
* `Dirstate`의 스레드 안전성은 명시되어 있지 않습니다. `HgRepository`의 변경 컨텍스트는 스레드별입니다.

`Revlog`, `RevlogIndex` (`storage` 패키지)::
* 스레드 안전성: 공개 메서드는 인스턴스별로 `synchronized`입니다. 저장소 잠금은 잡지 않습니다.
* 읽기에는 잠금이 필요 없습니다. `getRevisionContent(rev)`는 앞의 메타데이터 블록(복사 정보)을 떼어 내고, 가장 최근에 쓴 100개의 결과를 캐시하며 복사본을 돌려줍니다. `getRawRevisionContent(rev)`는 저장된 텍스트를 그대로 돌려줍니다. `rev` = -1은 빈 배열이고, 범위를 벗어난 리비전 번호는 `HgRevisionNotFoundException`을, 검열된 리비전은 `getRevisionContent`에서 `HgCensoredContentException`을 던집니다.
* 쓰기에는 저장소 잠금(`HgRepository.lockStore()`)이 필요합니다: `appendRevision(...)`과 그 오버로드, `appendRawRevision`, `appendOptimizedRevision`, `truncate`. 이 메서드들은 잠금을 잡지 않고 쥐고 있는지도 검사하지 않습니다.
* `appendRevision`은 파일을 쓰고 동기화하며, 메모리 인덱스와 persistent nodemap을 갱신하고, inline revlog가 131072바이트에 이르면 인덱스와 데이터 파일로 나눕니다. 리비전은 `parent1` 대비 델타가 더 작고 체인이 100보다 짧으면 델타로 저장하며, 첫 리비전과 매니페스트, changelog 리비전은 전체를 저장합니다.
* 노드 id 규칙: 두 부모 노드 id(바이트 오름차순)와 저장되는 텍스트(메타데이터가 있으면 메타데이터 블록이 앞에 붙은 내용)에 대한 SHA-1입니다. 그 노드 id의 리비전이 이미 있으면 아무것도 쓰지 않고 기존 노드 id를 돌려줍니다. 외부 저장(LFS) 리비전은 다른 바이트에 대해 해시를 계산할 수 있습니다(`hashBasisOverride`).
* `appendRawRevision`, `appendOptimizedRevision`은 호출자가 준 노드 id를 그대로 기록하고, 버전 1 레코드를 쓰며(버전 2 처리 없음), 노드가 내용과 맞는지와 중복 여부를 검사하지 않습니다. revlog를 복원하거나 다시 쓰는 용도입니다.
* `truncate(keepCount)`는 파일을 줄입니다. 자르기 전의 파일에서 읽은 `Revlog`에서 인스턴스마다 한 번만 호출하십시오. 이후 그 인스턴스는 낡은 상태이므로 다시 열기 전에 저장소의 revlog 캐시를 비워야 합니다. 호출자가 저장소 잠금을 쥐고 자르기를 저널에 기록합니다.
* 인덱스 레코드는 0부터 번호가 붙습니다. `getRevisionCount()`는 다른 쓰기 주체의 변경이 있는지 인덱스 파일을 다시 확인합니다. `findRevision(byte[])`는 앞 20바이트를 쓰며 모르는 노드는 -1을 돌려줍니다. `IndexRecord`의 노드 필드는 32바이트이고 앞 20바이트가 노드 id입니다.

`TreeWalk`, `TreeIterator`, `ManifestWalk`, `WorkingDirWalk` (`treewalk` 패키지)::
* 모두 스레드 안전하지 않고 잠금을 잡지 않습니다. 경로는 모두 UTF-8 오름차순으로 나옵니다.
* `TreeWalk`는 경로마다 한 번씩 트리들의 합집합을 방문합니다. `addTree`는 트리를 즉시 되돌리며, 트리의 인덱스는 추가한 순서입니다. `getNodeId(i)`는 노드 id가 없는 트리(작업 사본)에서는 `null`이고, `isSymlink(i)`는 `ManifestTreeIterator`에서만 `true`가 될 수 있습니다.
* `ManifestWalk`와 `WorkingDirWalk`는 첫 순회 전까지 아무것도 읽지 않습니다. 첫 `next()`가 매니페스트 전체(또는 작업 사본 전체)를 읽어 캐시하므로, 그 순간의 스냅숏이 됩니다. `reset()`은 커서만 되감고 다시 읽지 않습니다. 커서(`next()`, `getEntry()`)와 지연 뷰(`lazyEntries()`, `getEntries()`)는 하나의 읽기 객체를 공유하므로 인스턴스마다 한 방식만 쓰십시오.
* treemanifest 하위 디렉터리는 `ManifestWalk`가 펼쳐 주므로 파일만 나옵니다. `null`, 빈 문자열, `-1`, `null`(문자열) 리비전은 빈 순회입니다.
* `WorkingDirTreeIterator`는 디스크의 파일과 dirstate의 모든 경로를 돌려줍니다. dirstate에 없는 경로의 상태는 `?`입니다.

`ChangesetGraph`, `RevFilter`, `SortOrder` (`revwalk` 패키지)::
* `ChangesetGraph`는 changelog 인덱스에서 부모 링크를 읽습니다. 설정은 동기화되지 않으며, 인스턴스가 리비전 쌍별로 조상 질의 결과를 캐시하므로(캐시 접근은 동기화됩니다) 부모 조회 함수는 일관되게 쓰고 스레드마다 인스턴스를 따로 두십시오.
* `lazyAncestors(rev)`는 한 번만 쓸 수 있고 스레드 안전하지 않은 반복자를 돌려줍니다. `SortOrder.DEFAULT`에서는 너비 우선이며 지연 평가하고, `SortOrder.TOPO`에서는 전체 조상을 먼저 계산하여 모든 리비전이 부모보다 앞에 나옵니다. 부모가 없음은 `-1`입니다. `getAllAncestors`, `isAncestor`, `getLcaCandidates`는 필터를 무시하며, 리비전은 자기 자신의 조상입니다.
* `MaxCountRevFilter`는 상태를 가지므로 순회마다 새 인스턴스를 쓰거나 `reset()`을 호출하십시오.

`Merge3`, `MergeState` (`merge` 패키지)::
* `Merge3.merge(base, yours, theirs)`는 줄 목록에 대한 순수 함수입니다. 충돌한 블록에는 충돌 표시가 들어가고 `isConflicted()`가 `true`가 됩니다.
* `MergeState`는 실제 `hg resolve`가 쓰는 형식으로 `.hg/merge/state2`를 읽고 씁니다. `read`는 잠금을 잡지 않으며 없는 파일에는 활성이 아닌 상태를 돌려줍니다. `write`는 임시 파일 없이 제자리에서 덮어쓰므로, 병합 상태가 바뀌는 동안 `wlock`을 쥐고 있어야 합니다. `addMergedFile`, `markResolved`, `markUnresolved`의 변경은 `write` 전까지 메모리에만 있습니다.

`PhaseRoots` (`phase` 패키지)::
* `new PhaseRoots(File)`은 파일을 한 번 읽습니다. `setPhase`는 루트를 바꾸고 즉시 파일에 씁니다. 잠금은 잡지 않습니다. 파일이 `.hg/store/phaseroots`에 있으므로 다른 프로세스가 쓸 수 있다면 저장소 잠금을 쥐십시오.
* `getRoots(phase)`는 그 phase의 모든 변경집합이 아니라 기록된 경계 노드를 돌려줍니다. `getPhase`는 조상을 따라 실효 phase를 계산하며 부모 조회 함수나 changelog를 씁니다. `null` 노드와 널 노드는 public입니다.

`ObsStore`, `HgObsMarker`, `HgObsolescenceParser` (`obsolete` 패키지)::
* `ObsStore.read`는 obsstore의 두 버전(0과 1)을 모두 이해하고, `HgObsolescenceParser.parse`는 버전 1만 이해합니다. `HgObsMarker`는 방어적 복사를 하는 변경할 수 없는 마커입니다.
* `ObsStore.pushMarker`는 스스로 저장소 잠금을 잡습니다. `HgObsMarker.writeMarker(storeDir, ...)`는 `obsstore`에 버전 1 마커를 덧붙이며 잠금을 잡지 않습니다.

==== 예제
작업 사본 잠금을 쥔 채 dirstate를 바꿉니다. 잠금을 먼저 잡고, 가장 바깥 컨텍스트가 예외 없이 끝날 때 dirstate를 한 번 씁니다. 컨텍스트 안에서 `writeDirstate`를 호출해야만 변경이 디스크에 반영됩니다.

[source,java]
----
import io.github.search5.hg4j.dirstate.Dirstate;
import io.github.search5.hg4j.lib.HgLock;
import io.github.search5.hg4j.lib.HgRepository;
import java.io.File;

HgRepository repo = new HgRepository(new File("/path/to/repo"));
try (HgLock wlock = repo.lockWorkingCopy()) {
    repo.changingFiles(() -> {
        Dirstate dirstate = repo.getDirstate();       // 컨텍스트의 인스턴스
        dirstate.addEntry("docs/new.txt",
                new Dirstate.Entry('a', 0100644, -1, Dirstate.Entry.AMBIGUOUS_TIME));
        repo.writeDirstate(dirstate);                  // 컨텍스트가 끝날 때까지 미뤄집니다
        return null;
    });                                                // 여기서 dirstate가 기록됩니다
}
----

`Revlog`와 `ChangesetGraph`로 이력을 읽습니다. 읽기에는 잠금이 필요 없습니다.

[source,java]
----
import io.github.search5.hg4j.lib.HgRepository;
import io.github.search5.hg4j.lib.NodeId;
import io.github.search5.hg4j.revwalk.ChangesetGraph;
import io.github.search5.hg4j.revwalk.MaxCountRevFilter;
import io.github.search5.hg4j.revwalk.SortOrder;
import io.github.search5.hg4j.storage.Revlog;
import java.io.File;
import java.util.Arrays;
import java.util.Iterator;

HgRepository repo = new HgRepository(new File("/path/to/repo"));
Revlog changelog = repo.getRevlog(
        new File(repo.getStoreDir(), "00changelog.i"),
        new File(repo.getStoreDir(), "00changelog.d"));
int tip = changelog.getRevisionCount() - 1;

ChangesetGraph graph = new ChangesetGraph(changelog);
graph.setSortOrder(SortOrder.TOPO);
graph.setRevFilter(new MaxCountRevFilter(10));          // 순회마다 새 필터를 씁니다
for (Iterator<Integer> it = graph.lazyAncestors(tip); it.hasNext(); ) {
    int rev = it.next();
    Revlog.IndexRecord rec = changelog.getIndexRecord(rev);
    String node = new NodeId(Arrays.copyOf(rec.getNodeId(), 20)).toHex();
    byte[] text = changelog.getRevisionContent(rev);
    System.out.println(rev + " " + node + " parents " + rec.getParent1() + "," + rec.getParent2()
            + " (" + text.length + " bytes)");
}
----

[[locking]]
== 4. 잠금과 트랜잭션
hg4j는 원본 `localrepo.wlock()`과 `localrepo.lock()`의 순서와 범위를 따릅니다. 두 행위자를 동시에 시작하는 테스트(`LockScopeConcurrencyTest`)와 실제 `hg`와 겨루는 테스트(`RealHgLockContentionInteropTest`)가 이 규칙을 검증합니다.

* 작업 사본을 바꾸는 명령은 `wlock`을 먼저 잡고, 저장소에 쓸 때는 그 뒤에 `lock`을 잡습니다. 쓰는 구간만이 아니라 명령 전체에서 잠금을 쥐고 있다가 역순으로 풉니다. 배관은 이 순서를 강제하지 않으므로, `lockWorkingCopy()`와 `lockStore()`를 직접 쓰는 호출자가 순서를 지켜야 합니다.
* `lockWorkingCopy()`는 아무것도 복구하지 않습니다. `lockStore()`와 `lockStore(int)`는 `store/journal`이 있고 해당 스레드가 이미 잠금을 쥐고 있지 않으면 `HgAbandonedTransactionException`으로 거부하며, 예외를 던지기 전에 잠금을 다시 풉니다. 이때는 `RecoverCommand`(`hg recover`)를 실행해야 합니다. `lockStoreWithoutRecovery(int)`는 이 검사 없이 저장소 잠금을 잡으며, 잠금을 쥔 채 저널을 살펴봐야 하는 `recover`와 `verify`가 씁니다. 저장소를 고치는 것은 명시적인 `recover`와 `rollback`뿐이고, 둘 다 dirstate는 건드리지 않습니다.
* 다른 프로세스(또는 스레드)가 쥔 잠금은 `[ui] timeout`(기본 600초)까지 기다린 뒤 `HgLockException`을 던집니다. `ui.timeout = 0`이면 즉시 실패합니다. 시스템 속성 `hg4j.ui.timeout`은 기본값만 바꾸며, 명시한 `[ui] timeout`이 항상 우선합니다. `lockWorkingCopy(int)`와 `lockStore(int)`는 대기 시간을 밀리초로 받습니다. 잠금을 쥔 스레드에서는 다시 잡을 수 있습니다.
* 잠금이 풀린 뒤에 실행해야 하는 작업(커밋 후 훅 등)은 `afterLock`에 등록하며, 그 저장소에서 스레드가 쥔 마지막 잠금이 닫힌 뒤 한 번 실행됩니다(쥔 잠금이 없으면 즉시 실행됩니다). 이런 작업이 실패해도 기록만 하고 동작을 실패시키지 않습니다.
* 잠금 파일은 원본과 같은 것(`.hg/wlock`, `.hg/store/lock`)이어서, hg4j와 실제 `hg`가 서로를 배제합니다. server-shapes 갱신은 세 번째 파일 `.hg/store/store-shapes-lock`(`lockStoreShapes(int)`)을 쓰며, 저장소 잠금보다 먼저 잡습니다.
* 어떤 동작에 어떤 잠금이 필요한지: revlog, 매니페스트, dirstate 읽기에는 필요 없습니다. `Revlog` 덧붙이기와 `truncate`에는 저장소 잠금이, dirstate와 병합 상태를 바꿀 때는 작업 사본 잠금이 필요합니다. phase 루트와 폐기 마커는 저장소 안에 있습니다(<<plumbing-contracts>> 참고).

[[dirstate-contexts]]
=== 4.1 dirstate 컨텍스트
원본의 `dirstate.changing_files()`, `dirstate.changing_parents()`와 같습니다. `repo.changingFiles(body)`, `repo.changingParents(body)`로 쓰며, 본문을 람다로 쓸 수 없으면 `DirstateChange`를 돌려주는 `repo.openChangingFiles()`, `repo.openChangingParents()`로 열어 닫습니다.

* 둘 다 작업 사본 잠금이 필요하고 서로 배타적입니다. 한 종류가 열려 있을 때 다른 종류를 열면 `IllegalStateException`이 발생합니다. 같은 종류끼리는 중첩할 수 있으며 스레드별로 동작합니다.
* dirstate는 가장 바깥 컨텍스트가 정상적으로 끝날 때 한 번만 쓰이며, 컨텍스트 안에서 `writeDirstate`를 호출했을 때만 쓰입니다. `getDirstate()`는 컨텍스트 전체에서 같은 인스턴스를 돌려줍니다.
* `changingFiles`나 `changingParents` 안에서 예외가 나면 컨텍스트 전체가 무효가 되어 아무것도 쓰지 않으며, 다음 읽기는 디스크로 돌아갑니다. `openChanging...()`을 쓸 때는 작업이 실패했다면 `close()` 전에 `DirstateChange.failed()`를 호출해야 합니다. 그냥 `close()`하면 예외 때문에 빠져나오는 try-with-resources 블록에서도 dirstate를 씁니다.
* dirstate는 저널에 기록하지 않습니다. 메모리에서 바꾼 명령이 끝에서 한 번 씁니다. 저장소 트랜잭션을 여는 명령(예: `commit`)은 원본이 finalize 이후의 파일 생성기로 쓰는 것처럼 트랜잭션이 닫힌 뒤에 dirstate를 쓰고, 명령이 실패하면 아무것도 쓰지 않습니다.
* 추적 파일을 바꾸는 명령은 `changing_files`를 씁니다: `add`, `forget`, `remove`, `copy`/`rename`, `revert`. 부모를 바꾸는 명령은 `changing_parents`를 씁니다: `commit`, `update`, `merge`, `backout`, `graft`, `histedit`, `rebase`, `strip`, `bisect`, `pull`, `clone`, `unshelve`.
* dirstate를 직접 바꾸는 코드는 작업 사본 잠금을 쥐고 있어야 하며, 잠금 없이 컨텍스트를 열면 `IllegalStateException`("trying to change the dirstate without holding the wlock")이 발생합니다. 컨텍스트 밖에서 `Dirstate.write`를 직접 호출하면 잠금을 잡지도 검사하지도 않습니다.

[[dirstate-storage]]
=== 4.2 dirstate 저장
dirstate-v2는 Mercurial과 같게 저장합니다. docket 파일(`dirstate`)이 데이터 파일(`dirstate.<uid>`)을 가리킵니다. `Dirstate.write`는 새 항목을 데이터 파일 끝에 덧붙이고 docket을 마지막에 원자적으로 교체하므로, 읽는 쪽에는 이전 상태나 새 상태 중 하나만 보입니다. 디스크의 파일이 읽었던 것과 달라졌거나 데이터 파일의 절반 이상에 도달할 수 없으면, 새 uid로 새 데이터 파일을 쓰고 docket을 교체한 뒤 이전 데이터 파일을 지웁니다. v1 dirstate는 통째로 원자적으로 교체합니다. `HgRepository.writeDirstate`는 쓸 때마다 저장소의 `dirstate-v2` requirement로 형식을 정합니다.

== 5. 저장소 형식
아래의 모든 requirement 이름은 코드 검색으로 확인했습니다(`HgRepository`, `InitCommand`, `Hg.open`, `NarrowCloneCommand`가 읽거나 쓰는 이름입니다).

* 저장소: `store`, `fncache`, `dotencode`, `generaldelta`, `revlogv1`, `share-safe`, 공유 저장소(`shared`, `relshared`, `sharedpath`), `fileindex-v1`. `sparserevlog`는 `Hg.open`과 clone bundle 선택이 받아들이지만 `InitCommand`가 쓰지 않으며 이 이름에 따라 동작하는 hg4j 코드는 없습니다.
* revlog: revlog-v1, `exp-revlogv2.2`(docket), `exp-changelog-v2`와 `exp-copies-sidedata-changeset`(변경집합의 변경 파일을 sidedata에 보관), `persistent-nodemap`, `revlog-compression-zstd`.
* 작업 사본: dirstate-v1과 `dirstate-v2`.
* 그 밖: `treemanifest`, requirement `narrowhg-experimental`과 파일 `narrowspec`, `narrowspec.dirstate`를 쓰는 narrow 클론, requirement가 아니라 wire capability `exp-shape-1`을 쓰는 shape와 shard, hg4j가 읽기만 하고(`getRequirements().contains("lfs")`) 쓰지 않는 `lfs`.
* changegroup 01~05(05는 sidedata 포함), bundle2(`HG20`)의 GZ, BZ, ZS 압축, 스트림 클론, clone bundle.

미구현: `internal-phase`(그래서 `strip --soft`는 거부됩니다. 의도적 차이 절 참고)와 `dirstate-tracked-hint-v1`(clone bundle의 requirement 목록에서 허용만 합니다).

`Hg.open(File)`은 `.hg/requires`와 `.hg/store/requires`의 모든 줄을 허용 목록과 비교하며, 그 밖의 이름이면 `HgValidationException`("unsupported repository requirement")을 던집니다. 허용 목록은 `dotencode`, `fncache`, `generaldelta`, `revlogv1`, `store`, `dirstate-v2`, `share-safe`, `sparserevlog`, `revlog-compression-zstd`, `exp-changelog-v2`, `exp-revlogv2.2`, `persistent-nodemap`, `fileindex-v1`, `treemanifest`, `exp-copies-sidedata-changeset`, `narrowhg-experimental`, `lfs`, `shared`, `relshared`입니다. `Repository.open`과 `new HgRepository(File)`은 이 검사를 하지 않습니다.

`InitCommand`는 보수적인 집합(`revlogv1`, `store`, `fncache`, `dotencode`, `generaldelta`)을 만듭니다. 새 형식은 `hg`에서 설정으로 켜듯이 설정자로 켭니다. Mercurial 7.2는 dirstate-v2와 파일 인덱스를 정식 기능으로 올렸지만 Rust 확장과 함께 쓸 때만 권장합니다. hg4j에는 이런 제한이 없습니다.

== 6. 상호운용성과 테스트
* `./gradlew test`는 단위 테스트를, `./gradlew interopTest`는 `interop` 태그가 붙은 테스트를 실행합니다. 후자는 실제 `hg`가 필요하며(`PATH`, 그리고 dirstate-v2와 shape 테스트용으로 `~/.cache/hg4j/`의 Rust 빌드), 약 1시간 30분이 걸립니다.
* **요구사항 매트릭스**는 한 명령을 저장소 형식 36개 조합에서 hg4j와 실제 `hg`로 각각 실행해 결과를 비교합니다. **와이어 매트릭스**는 HTTP와 SSH에서 hg4j 또는 실제 클라이언트와 hg4j 또는 실제 서버의 조합을 같은 방식으로 비교합니다.
* **잠금 경쟁 테스트**는 hg4j와 실제 `hg`가 한 저장소에 동시에 쓰게 합니다. 시나리오마다 두 번 실행합니다. 잠금을 켠 채로는 아무것도 손상되면 안 되고, 실제 `hg`의 잠금은 그대로 두고 hg4j의 잠금만 테스트 훅으로 끈 채로는 손상이 드러나야 합니다. 잠금 없이도 통과하는 시나리오는 잠금을 검증하지 못하는 것입니다.
* 빌드는 커버리지를 검사합니다. 전체 70%, 핵심 클래스별 90%입니다(`jacocoTestCoverageVerification`). 보고서에는 단위와 interop 실행 결과를 합칩니다. `-PignoreTestFailures`를 주면 테스트가 실패해도 전체 실행이 커버리지 보고서까지 진행됩니다.

== 7. Mercurial과 의도적으로 다른 부분
* `shelve`: 원본처럼 보관 단계 전체를 감싸는 컨텍스트는 없습니다. 임시 커밋이 자기 컨텍스트를 열고, 작업 사본의 부모로 돌아가는 부분은 `changing_parents`에서 실행합니다(원본은 `update`로 처리합니다). `unshelve`는 `changing_parents`를 씁니다. 보관 단계 전체를 하나의 컨텍스트로 감싸면 임시 커밋의 부모가 남아서 `unshelve`가 깨집니다.
* `status`: stat 보정(깨끗하다고 확인되었지만 기록된 stat이 낡은 파일)은 `_poststatusfixup`처럼 `changing_*` 컨텍스트 없이 `wlock(wait=False)`로 씁니다. 원본은 status를 `running_status` 컨텍스트에서 실행하는데, 이 컨텍스트는 `changing_*`와 배타적이지 않고 잠금도 요구하지 않으며, 그 뒤에 기다리지 않고 잠금을 시도합니다. hg4j에는 `running_status` 객체가 없지만 단계는 같습니다. 보정은 status가 본 값을 여전히 가진 항목에만 적용하고(원본은 잠금을 잡는 사이 디스크의 dirstate가 바뀌면 버립니다), 잠금이 비어 있으면 쓰고, 없으면 버립니다(`LockError`). 그 밖의 실패는 삼키지 않습니다.
* `sign --force`는 동작합니다. 원본에서는 `UnboundLocalError`로 끝납니다.
* `strip --soft`는 명확한 메시지와 함께 거부합니다. 기본 저장소에서 원본은 archived 단계에 `internal-phase` 요구사항이 필요해서 예외로 실패합니다.
* `upgrade`(`debugupgraderepo`)는 제공하지 않습니다. 다음 메이저 버전에서 명령행 인터페이스와 함께 추가할 예정입니다.
* 빈 shard 이름으로 `store_shape`를 요청하면 원본처럼 응답이 없습니다(원본은 실패합니다).
* 원본을 따라서 호출하는 쪽이 알아챌 수 있는 동작: `rebase --abort`, `unshelve --abort`, 충돌한 `backout` 뒤에 `.orig` 파일이 남습니다. evolution이 꺼진 `rebase`는 원본 변경집합을 제거합니다. 다른 이력 계통에 있는 브랜치 이름을 다시 쓰려면 `-f`가 필요합니다. `phase`가 더 높은 단계로의 이동을 거부하면 종료 코드 1과 `cannot move N changesets to a higher phase, use --force` 메시지를 냅니다. `sign`은 `.hgsigs`만 커밋합니다.

== 호출하는 쪽에 필요한 API 변경
아래 변경은 이전 API로 작성한 코드에서 조치가 필요합니다. `HgLockException`은 검사 예외(`HgException`이 `Exception`을 상속)이므로, 바뀐 메서드를 호출하는 쪽은 잡거나 선언해야 합니다.

[cols="2,3,4"]
|===
|대상 |변경 |조치

|`BisectCommand.next()`, `BookmarkCommand.call()`, `BranchCommand.call()`, `CensorCommand.call()`, `GcCommand.call()`, `RecoverCommand.call()`, `ResolveCommand.call()`, `RollbackCommand.call()`, `VerifyCommand.call()`, `Hg.rollback()`
|`throws HgLockException`을 선언합니다(잠금을 스스로 잡습니다).
|`HgLockException`을 잡거나 선언합니다. 하위 클래스 `HgAbandonedTransactionException`은 중단된 트랜잭션의 저널이 발견되었다는 뜻입니다.

|`HgRepository.lockStore(int)`
|중단된 트랜잭션을 더 이상 복구하지 않습니다. 다른 잠금 보유자가 남긴 저널이 있으면 `HgAbandonedTransactionException`을 던집니다.
|`RecoverCommand`를 실행한 뒤 다시 잠급니다. `lockStoreWithoutRecovery(int)`는 `recover`와 `verify`가 잠금을 쥔 채 저널을 살펴보려고 쓰는 변형입니다.

|`HgRepository.getDirstate()`와 `Dirstate` 직접 변경
|dirstate를 바꾸려면 작업 사본 잠금이 필요하며, 쓰기는 dirstate 컨텍스트가 끝날 때 일어납니다.
|`lockWorkingCopy()`를 쥔 상태에서 `changingFiles(...)` 또는 `changingParents(...)`(또는 try-with-resources로 `openChangingFiles()`, `openChangingParents()`)를 씁니다. 잠금이 없으면 `IllegalStateException`이 발생합니다.

|`HgRepository.DirstateBody<T>`
|새 함수형 인터페이스이며 `run()`은 `IOException`과 `HgLockException`을 던질 수 있습니다.
|`changingFiles`, `changingParents`에 넘깁니다.

|`HgRepository.afterLock(AfterLockAction)`
|새 기능입니다. 가장 바깥 잠금이 풀린 뒤 실행할 작업을 등록합니다.
|잠금 안에서 실행하면 안 되는 후속 작업에 씁니다.

|`dirstate.backup`, `dirstate` 저널 항목
|제거했습니다. 이 항목이 남은 이전 저널도 오류 없이 읽습니다.
|백업 파일을 읽는 도구는 더 이상 읽지 않도록 고쳐야 합니다.

|`RebaseCommand`
|`rebase.py`를 따릅니다. `call()`은 `setSource(byte[])`, `setTarget(byte[])`뿐 아니라 revset 설정자(`addSourceRevset`, `addBaseRevset`, `addRevisionRevset`, `setDestination`)로도 실행합니다. `setKeep(true)`가 아니면 원본을 strip하며, 상태 파일은 `.hg/rebasestate`입니다.
|원본이 계속 읽힐 것으로 기대한 코드를 고칩니다.

|`PhaseCommand.call()`
|더 높은 단계로의 이동 거부를 예외가 아니라 종료 코드(`getExitCode()`가 1)와 `getMessages()`로 알립니다.
|`getExitCode()`를 확인합니다.

|`SignCommand`
|`.hgsigs`만 커밋하며, 커밋이 실패해도 파일을 복원하지 않습니다.
|다른 변경은 직접 커밋합니다.

|`BranchCommand`
|다른 이력 계통에 있는 브랜치 이름을 다시 쓰려면 `setForce(boolean)`이 필요합니다.
|원본에서 `-f`가 필요한 곳에서 `true`를 넘깁니다.
|===

이전 코드에서 옮길 필요가 없는 새 명령과 옵션: `AdminVerifyCommand`, `ChainsawUpdateCommand`, `GraftInMemory`(`graft --to`), `NarrowServerAdmin`, `ShardedStreamBundlesCommand`, `UnshareCommand`. `AddCommand`와 `AddremoveCommand`의 `setSubrepos`. `CloneCommand`, `PullCommand`, `FetchCommand`의 `setPull`, `setStream`, `getMessages()`. 파일 명령의 패턴, include, exclude, cwd 설정자.

== 8. 알려진 문제와 남은 과제
=== 8.1 한계
* **Mercurial 버전**: 7.2와 7.2.4에서만 검증했습니다. 기본 설정으로 만든 저장소는 오래된 요구사항만 쓰므로 이전 7.x 릴리스에서도 열릴 것으로 예상하지만 검증하지 않았습니다. 새 형식은 그것을 도입한 Mercurial 릴리스가 필요합니다.
* **적용한 changegroup의 sidedata**: sidedata가 없는 changegroup(버전 01~04)을 변경 파일 sidedata를 유지하는 저장소에 적용하면 변경 파일을 매니페스트에서 계산합니다. 복사 정보는 이렇게 유도할 수 없어서 기록하지 않습니다. changegroup 05는 복사 정보를 포함한 자체 sidedata를 그대로 유지합니다.
* **미구현**: HTTP 와이어 프로토콜 버전 2, `largefiles`, `dirstate-tracked-hint`, `upgrade`.

=== 8.2 미해결 사항
* `TransportE2EMatrixInteropTest`의 실제 클라이언트와 실제 서버 조합("head를 만드는 push는 거부된다")이 전체 실행 4회 중 2회 실패했고, 단독 실행에서는 매번 통과했습니다. 양쪽이 모두 실제 `hg`여서 알려진 범위에서는 hg4j 코드와 무관하지만 원인은 찾지 못했습니다.

=== 8.3 발견되어 수정된 주요 결함
* changelog-v2와 sidedata를 쓰는 저장소에서 리베이스하면 변경 파일 sidedata가 없는 변경집합이 만들어져 `hg verify`가 무결성 오류를 냈습니다. 이제 다시 적용한 변경집합에도 sidedata를 만듭니다.
* 이미 sidedata를 담은 번들(changegroup 05)의 sidedata를 다시 계산하면 복사 정보가 사라졌습니다. 이제 sidedata 없이 도착한 변경집합에만 계산합니다.
* LFS 리비전이 있는 저장소의 `strip`이 남기는 변경집합의 LFS 플래그를 잃어서(임시 번들이 changegroup 01이었습니다) 해시 불일치로 실패했습니다. LFS 저장소는 이 용도로 changegroup 03을 씁니다.
* `unshelve`가 리베이스된 복원 커밋을 저장소에 남겼고, `unshelve --abort`가 `.hg/rebasestate`와 병합 상태를 지우지 않았습니다.
* 쓰는 구간만 덮던 잠금 때문에, 거부된 push가 동시에 도착한 push를 되돌리거나 두 `tag` 명령 중 하나의 태그가 사라질 수 있었습니다. 이제 잠금이 명령 전체를 덮습니다.
* dirstate를 명령 중간에 쓰고 명령이 실패하면 백업 파일로 되돌렸습니다. 이제 트랜잭션이 끝난 뒤 한 번만 쓰고, 실패하면 쓰지 않습니다.
* 클래스별 전체 목록과 원인, 수정 내용은 `llm-wiki/known-bugs-registry.md`에, 잠금 작업의 진행 상태는 `llm-wiki/lock-parity-matrix.md`에 있습니다.
