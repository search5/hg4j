== 유지보수와 무결성 명령

=== VerifyCommand

저장소 store의 무결성을 검사합니다. `hg verify`에 대응합니다. javadoc은 이를 "simplified verifier"라고 부릅니다. changelog, manifest, `meta/` 아래의 treemanifest 하위 manifest, 모든 filelog의 노드 ID 해시 일관성을 검사하며, changelog, manifest, filelog 사이의 연결 관계는 교차 검증하지 않습니다.

[cols="2,5"]
|===
|메서드 |의미

|`VerifyCommand(HgRepository)` |생성자입니다. 저장소가 null이면 `IllegalArgumentException`이 발생합니다.
|`setSkipLfs(boolean)` |`hg verify --no-lfs`입니다. 로컬에 없는 LFS blob을 읽지(따라서 가져오지) 않습니다. 설정 `verify.skipflags`에 EXTSTORED 비트(0x2000)가 있어도 같은 효과입니다.
|===

실행:: `List<String> call() throws HgLockException`. 오류 메시지 목록을 반환하며, 빈 목록은 검사에서 발견된 것이 없다는 뜻입니다. 검사 중의 읽기 실패는 던지지 않고 `critical repository read failure: ...` 메시지로 보고합니다. 잠금 해제 실패는 `HgLockException`으로 다시 던집니다. `00changelog.i`가 없는 저장소는 실제 hg처럼 빈 changelog(0 리비전)로 취급합니다. `00manifest.i`가 없는 경우는 changelog에 리비전이 있을 때만 오류입니다. filelog는 `fncache`와 `data/` 순회 결과를 합쳐 찾으며, 인덱스 파일이 없는 `fncache` 항목은 보고합니다.

잠금:: `lockStoreWithoutRecovery`로 잡는 store 잠금 하나뿐이며, 검사 전체를 감쌉니다("Like real hg (verify.verify)"). 작업 사본 잠금은 잡지 않습니다. dirstate는 건드리지 않습니다.

hg 원본과 다른 점:: 위에서 설명한 단순화된 검사기입니다(연결 관계 교차 검증 없음). 그 밖에는 소스에 적혀 있지 않습니다.

[source,java]
----
try (Hg hg = Hg.open("/path/to/repo")) {
    List<String> errors = hg.verify().setSkipLfs(true).call();
    if (!errors.isEmpty()) errors.forEach(System.err::println);
}
----

=== RecoverCommand

중단된 트랜잭션(남아 있는 `.hg/store/journal`)을 되돌립니다. `hg recover`와 `hg recover --verify`에 대응합니다.

[cols="2,5"]
|===
|메서드 |의미

|`RecoverCommand(HgRepository)` |생성자입니다. 저장소가 null이면 `IllegalArgumentException`이 발생합니다.
|`setVerify(boolean)` |`hg recover --verify`입니다. 중단된 트랜잭션을 발견해 되돌린 경우에만 `VerifyCommand`를 추가로 실행하고 그 오류를 결과에 담습니다.
|===

실행:: `RecoverResult call() throws HgLockException`. 결과는 `wasInterrupted()`(journal을 발견했는지, false는 실제 hg의 "no interrupted transaction available"), `isSuccess()`(복구할 것이 없었거나 되돌림에 성공했는지, false는 되돌림을 끝내지 못해 재시도를 위해 journal을 남겼다는 뜻), `getVerifyErrors()`(verify를 실행하지 않았으면 null, 빈 목록은 발견된 오류 없음)를 제공합니다. "복구할 것 없음"은 예외가 아니라 결과로 반환합니다.

잠금:: `lockStoreWithoutRecovery`로 잡는 store 잠금 하나뿐입니다(이 잠금은 스스로 복구하지 않습니다). 작업 사본 잠금은 잡지 않습니다. 되돌림은 `HgRepository.checkAndPerformAutoRollback()`에 위임하며, 이 메서드는 journal로 store 파일을 복원하고 dirstate는 절대 건드리지 않습니다(코드 주석: 트랜잭션 복구는 dirstate를 바꾸지 않으며, dirstate는 트랜잭션 뒤에 기록됨). 잠금 대기에는 저장소의 push 잠금 대기 시간을 씁니다. `setVerify(true)`가 적용되면 `VerifyCommand.call()`이 같은 잠금을 쥔 채 실행됩니다. journal이 없으면 아무것도 하지 않습니다.

hg 원본과 다른 점:: 종료 코드나 메시지 대신 `RecoverResult`를 반환하며, "복구할 것 없음"(실제 hg는 `no interrupted transaction available`, 종료 코드 1)은 오류가 아니라 정상 결과입니다. 그래서 라이브러리 호출자가 저장소를 열기 전의 상태 점검으로 실행할 수 있습니다.

[source,java]
----
RecoverCommand.RecoverResult r = hg.recover().setVerify(true).call();
if (r.wasInterrupted() && !r.isSuccess()) {
    System.err.println("journal kept for retry");
}
----

=== RollbackCommand

`undo*` 파일을 사용해 마지막 트랜잭션을 되돌립니다. `hg rollback`에 대응합니다.

[cols="2,5"]
|===
|메서드 |의미

|`RollbackCommand(HgRepository)` |생성자입니다. 설정자는 없습니다.
|===

실행:: `void call() throws IOException, HgLockException`. `Hg.rollback()`으로도 호출할 수 있습니다(예외는 같음). 작업 디렉터리 잠금과 저장소 잠금을 저장소의 push 잠금 대기 시간까지 기다리며 잡습니다. `store/undo`가 없으면 `IllegalStateException("No rollback information available (undo file not found)")`, 파일 복원이 실패하면 `IOException`, 대기 시간 안에 잠금을 잡지 못하면 `HgLockException`을 던집니다. 단계는 다음과 같습니다. (1) `undo`를 읽어 store 파일을 자르거나 삭제합니다(`trunc` 줄은 자르기만 하고, `backup` 줄은 v2 docket revlog의 전체 파일 바이트를 복원하며, 일반 줄은 기록된 크기로 자르거나 크기 0이면 삭제합니다). (2) `.hg/undo.backup.dirstate`에서 `.hg/dirstate`를 복원하고(백업이 없으면 `dirstate`를 삭제), docket이 가리키는 uid 데이터 파일이 없으면 `.hg/undo.backup.dirstate.data`에서 dirstate-v2 데이터 파일을 복원합니다. (3) `.hg/undo.backup.bookmarks`에서 `.hg/bookmarks`를 복원하고(없으면 삭제) `.hg/bookmarks.current`를 삭제합니다. (4) `finally`에서 모든 `undo*` 정보 파일과 사용한 docket 백업을 삭제하고 revlog 캐시를 비웁니다.

잠금:: 먼저 `lockWorkingCopy(timeout)`, 다음에 `lockStore(timeout)`입니다. `HgRepository.lockStore`는 journal이 있고 잠금이 재진입이 아니면 `HgAbandonedTransactionException`으로 거부합니다. 두 잠금 모두 첫 읽기 전에 잡고 명령이 끝날 때 해제합니다. rollback은 dirstate와 bookmarks를 실제로 수정합니다.

hg 원본과 다른 점:: 클래스 javadoc의 `undo.*` 배치 준수 설명 외에는 적혀 있지 않습니다.

[source,java]
----
hg.rollback();
// 또는
new RollbackCommand(hg.getRepository()).call();
----

=== GcCommand

store 압축과 정리입니다. 정확히 대응하는 hg 명령은 없으며, 소스는 가장 가까운 실제 hg 동작으로 `debugupgraderepo`와 `debugrebuildfncache`를 듭니다.

[cols="2,5"]
|===
|메서드 |의미

|`GcCommand(HgRepository)` |생성자입니다. 설정자는 없습니다.
|===

실행:: `String call() throws IOException, HgLockException`. `GC / Compaction complete: defragmented and re-delta optimized N store revlogs, cleaned M orphaned temp files.` 형태의 요약 문자열을 반환합니다. store 디렉터리가 없으면 `IOException`을 던집니다(잠금을 잡으면 디렉터리가 생기므로 가장 먼저 확인합니다). 단계는 다음과 같습니다. revlog 캐시를 비웁니다. store 루트의 `*.backup`, `*.tmp`, `journal` 파일을 삭제합니다. changelog, manifest, `data/`와 `meta/` 아래의 모든 `.i` revlog를 리비전 단위로 임시 파일에 다시 써서 원자적으로 교체합니다(빈 revlog와 v2/docket revlog는 건너뛰고 그대로 둡니다). `fncache`를 원자적 IO로 다시 만듭니다(`data/`와 `meta/` revlog 항목만, 분할 revlog는 `.d` 항목 포함이며, `fileindex-v1` 저장소이거나 찾은 것이 없으면 건너뜁니다). 마지막으로 `System.gc()`를 호출합니다.

잠금:: 먼저 `lockWorkingCopy(timeout)`, 다음에 `lockStoreWithoutRecovery(timeout)`입니다. 이 명령이 오래된 journal을 포함한 잔여물을 스스로 지우고 개수를 세기 때문입니다.

hg 원본과 다른 점:: 직접 대응하는 명령이 없습니다. v2/docket revlog(`changelog-v2`, `general-v2`)는 실제 hg에 압축 동작이 없고 다시 쓰면 파괴적이므로 절대 다시 쓰지 않습니다.

[source,java]
----
String summary = hg.gc().call();
System.out.println(summary);
----

=== AdminVerifyCommand

이름 붙은 저장소 검사를 실행합니다. `hg admin::verify`(`admin/verify.py`)에 대응합니다. Mercurial 7.2에서 등록된 검사는 `working-copy.dirstate`(별칭 `dirstate`) 하나이며, dirstate를 부모들의 manifest와 비교합니다.

[cols="2,5"]
|===
|메서드 |의미

|`AdminVerifyCommand(HgRepository)` |생성자입니다.
|`addCheck(String)` |`-c/--check`입니다. 실행할 검사를 추가합니다. 이름은 정규화된 이름, 별칭, 정규화된 이름의 접두사(`working-copy`는 그 아래를 모두 실행), 또는 `full`입니다. 하나도 없으면 호출이 실패합니다.
|`addOption(String)` |`-o/--option`입니다. 형식은 `check:option=value`입니다. 해당 검사가 그 옵션을 받아야 하는데, 등록된 유일한 검사는 옵션이 없습니다.
|`getOutput()` |`ui.status`가 출력한 줄입니다.
|`getWarnings()` |`ui.warn`이 출력한 줄입니다. 발견 사항과, journal이 있을 때의 `abandoned transaction found - run hg recover` 경고가 들어 있습니다.
|===

실행:: `Map<String, Integer> call() throws IOException`. 오류를 발견한 검사마다 정규화된 이름별 오류 개수를 반환합니다. 알 수 없는 검사, 잘못된 옵션, 선택되지 않은 검사에 대한 옵션, 검사에 없는 옵션, 선택된 검사가 없는 경우(`` `checks` required ``)에 `HgValidationException`(`IOException`)을 던집니다.

잠금:: 없습니다. 클래스 javadoc에 "Nothing is locked: it only reads."라고 적혀 있습니다.

hg 원본과 다른 점:: 등록된 검사가 하나뿐이라는 설명 외에는 적혀 있지 않습니다.

[source,java]
----
AdminVerifyCommand v = new AdminVerifyCommand(hg.getRepository()).addCheck("dirstate");
Map<String, Integer> found = v.call();
v.getWarnings().forEach(System.err::print);
----

=== NarrowServerAdmin

서버 저장소의 shard와 shape를 관리합니다. `hg admin::narrow-server`와 `admin::narrow-client`(`--store-fingerprint`)에 대응합니다. final 클래스이며 `call()`이 없고, 옵션마다 별도 메서드가 있습니다. 분석은 소스가 가리키는 `llm-wiki/concepts/store-shapes.md`의 10절과 11절에 있습니다.

[cols="2,5"]
|===
|메서드 |의미

|`NarrowServerAdmin(HgRepository)` |생성자입니다.
|`getWarnings()` |마지막 호출이 경고한 내용(`ui.warn`)입니다. 예를 들어 store shapes 갱신이 진행 중이라는 경고입니다.
|`shapeFingerprints()` |`--shape-fingerprints`입니다. 모든 shape에 대해 `<fingerprint> <names>` 줄을 반환합니다.
|`storeShardsListing()` |`--store-shards`입니다. 모든 shard의 id와, 있으면 `read-write-access=a,b`를 반환합니다.
|`shapePatterns(String names)` |`--shape-patterns NAMES`입니다. zero path 순서의 `inc:/path`, `exc:/path` 줄입니다.
|`shapeNarrowPatterns(String names)` |`--shape-narrow-patterns NAMES`입니다. 루트를 뺀 기존 `[include]`, `[exclude]` 섹션입니다.
|`shapeFiles(String names, boolean hiddenOnly)` |`--shape-files` / `--shape-files-hidden`입니다. shape가 포함하는 store의 filelog를 정렬해 반환하며, `hiddenOnly`이면 작업 사본에 없는 것만 반환합니다.
|`shapeUpdate(byte[] newContents, UpdateOptions options)` |`--shape-update`입니다. 검증 후 `server-shapes` 파일을 교체합니다. 헤더 주석이 없으면 앞에 붙입니다.
|`shapeClearPrevious()` |`--shape-clear-previous`입니다. 저장된 이전 설정을 지우고 `cleared N saved server-shapes`를 반환합니다.
|`static storeFingerprint(Set<String> includes, Set<String> excludes)` |`admin::narrow-client --store-fingerprint`입니다. narrow 클론의 store narrowspec 지문을 줄바꿈과 함께 반환합니다.
|`UpdateOptions(overrideReshapeAndReshardCheck, overrideFingerprintChangeCheck, overrideSavedConfigsCheck)` |`--shape-update`의 `override-*` 플래그 세 개를 담은 record입니다. `UpdateOptions.strict()`는 모두 false입니다.
|===

실행:: 목록 메서드는 `List<String>`을 반환하고 `IOException`을 던집니다. `shapeUpdate`는 void이며 `IOException, HgLockException`을 던집니다. `shapeClearPrevious`는 `String`을 반환하고 `IOException, HgLockException`을 던집니다. 모든 인스턴스 메서드는 `.hg/requires` 또는 `store/requires`에 `narrowhg-experimental`이 있으면 먼저 `HgValidationException("repo is narrowed, this is a server command")`을 던집니다. 알 수 없는 shape 이름은 `HgValidationException("shape '...' not found")`입니다. `shapeUpdate`의 검증(`HgValidationException`)은 기존 shape의 지문 변경, 한 번의 갱신에서 reshape와 reshard를 동시에 하는 것, 이전 설정이 아직 저장된 상태에서의 reshape를 거부하며, 각각 해당 override 플래그가 있으면 통과합니다.

잠금:: 목록 메서드는 잠금을 잡지 않고, 갱신이 진행 중이면 경고만 합니다. `shapeUpdate`는 먼저 대기하지 않는 store shapes 잠금(`lockStoreShapes(0)`)을 잡고, 이전 설정을 읽고, 새 설정을 파싱 및 검증한 뒤(잘못된 문서는 아무것도 쓰기 전에 중단), 쓰기 구간에서만 store 잠금(`lockStoreWithoutRecovery`)을 잡습니다. shard가 바뀌었으면 이전 설정을 먼저 저장하고 원자적으로 씁니다. `shapeClearPrevious`는 shapes 잠금과 store 잠금을 이 순서로 함께 잡습니다. 작업 사본 잠금은 잡지 않습니다.

hg 원본과 다른 점:: 적혀 있지 않습니다.

[source,java]
----
NarrowServerAdmin admin = new NarrowServerAdmin(hg.getRepository());
admin.shapeFingerprints().forEach(System.out::println);
admin.shapeUpdate(Files.readAllBytes(Path.of("server-shapes")), NarrowServerAdmin.UpdateOptions.strict());
----

=== ChainsawUpdateCommand

무엇이 있든 pull하고 지정한 리비전으로 update합니다. `hg admin::chainsaw-update`(`mercurial/admin/chainsaw.py`)에 대응합니다. javadoc은 이를 위험(DANGEROUS)하다고 표시합니다. 대상 위치에 저장소가 아닌 디렉터리가 있으면 삭제하고, 누가 쥐고 있든 잠금을 깨고, 로컬 변경과 알 수 없는 파일을 버립니다. 저장소를 단독으로 쓰는 무인 실행용입니다.

[cols="2,5"]
|===
|메서드 |의미

|`setRevision(String)` |`--rev`입니다. 대상 리비전이며 필수입니다.
|`setSource(String)` |`--source`입니다. pull할 위치이며 필수입니다.
|`setDestination(String)` |`--dest`입니다. update할 저장소이며, 없으면 새로 만듭니다. 필수입니다.
|`setPurgeUnknown(boolean)` |`--purge-unknown`이며 기본값은 켜짐입니다.
|`setPurgeIgnored(boolean)` |`--purge-ignored`이며 기본값은 켜짐입니다.
|`setInitialCloneMinimal(boolean)` |`--initial-clone-minimal`입니다. 저장소를 만들 때 해당 리비전만 pull합니다(그래서 clone bundle을 쓰지 않습니다).
|`getMessages()` |hg가 출력하는 대로 줄 단위로 사용자에게 알린 내용입니다.
|===

실행:: `void call() throws IOException, HgLockException`. 리비전, 소스, 대상 중 비어 있는 것이 있으면 `HgValidationException`, 어느 단계든 실패하면 `IOException`, 옛 잠금을 깬 뒤에도 잠금을 잡지 못하면 `HgLockException`을 던집니다. `<dest>/.hg`가 있으면 그 저장소를 불러오고, 없으면 그 위치의 것을 삭제한 뒤 `Hg.init()`으로 저장소를 만들고 `setInitialCloneMinimal(true)`가 아니면 전체를 pull합니다. 이어서 잠금 깨기, 복구, pull, purge, 강제 update 순으로 진행합니다.

잠금:: 원본과 같은 순서입니다. 먼저 `store/lock`과 `.hg/wlock` 파일을 아무것도 잡지 않고 삭제합니다(메시지 `had to break store lock`, `had to break working copy lock`). 그 다음 `lockWorkingCopy()`와 `lockStoreWithoutRecovery(timeout)`을 함께 잡고 복구(`RecoverCommand`), pull, purge(`PurgeCommand`, 디렉터리 포함, 파일은 purge unknown, ignored는 purge ignored), update(`UpdateCommand`, force)를 수행합니다. pull과 update는 같은 잠금을 다시 잡으며(재진입), purge는 자체 잠금을 잡지 않습니다.

hg 원본과 다른 점:: 위의 위험 안내 외에는 적혀 있지 않습니다.

[source,java]
----
ChainsawUpdateCommand c = new ChainsawUpdateCommand()
    .setSource("https://example.org/repo").setDestination("/srv/checkout").setRevision("default");
c.call();
c.getMessages().forEach(System.out::print);
----

== 서명 명령

세 명령 모두 `gpg` 확장(`hgext/gpg.py`) 형식을 사용하며, `GpgKeyring`이 필요합니다(`setKeyring`으로 지정).

=== SignCommand

GPG 키로 changeset에 서명합니다. `hg sign`에 대응합니다. 서명은 `.hgsigs`에 기록하고(커밋됨), `setLocal`을 쓰면 `.hg/localsigs`에 기록합니다(커밋되지 않음). 형식과 서명 대상 텍스트는 `gpg` 확장과 같으므로 `hg sigcheck`가 이 명령이 쓴 것을 받아들입니다.

[cols="2,5"]
|===
|메서드 |의미

|`setNodeId(byte[])` |서명할 changeset입니다(20바이트 노드). 기본값은 작업 디렉터리의 부모입니다.
|`setKeyring(GpgKeyring)` |서명에 쓸 키입니다. 비밀 키를 포함해야 합니다(`GpgKeyring.withSecretKeys`). 필수입니다.
|`setKeySpec(String)` |`hg sign --key`입니다. 사용자 id의 일부, 또는 키 id나 지문(접미사)입니다.
|`setPassphrase(char[])` |키의 암호입니다. 보호되지 않은 키는 null 또는 빈 값입니다.
|`setLocal(boolean)` |`--local`입니다. 버전 관리되지 않고 커밋되지 않는 `.hg/localsigs`에 씁니다.
|`setCommit(boolean)` |`--no-commit`은 `setCommit(false)`입니다. `.hgsigs`를 쓰고 추적하지만 커밋하지 않습니다. 기본값은 true입니다.
|`setForce(boolean)` |`--force`입니다. `.hgsigs`에 커밋되지 않은 변경이 있어도 서명합니다.
|`setMessage(String)` |커밋 메시지입니다. 기본값은 서명한 changeset마다 한 줄 `Added signature for changeset <short>`입니다.
|`setAuthor(String)` |`.hgsigs` 커밋의 작성자이며 보통 `Name <email>` 형식입니다. 기본값은 `hg4j <hg4j@google.com>`입니다. `setLocal`을 쓰거나 `setCommit(false)`이면 쓰이지 않습니다.
|`setSigningTime(Instant)` |서명 생성 시각입니다. 기본값은 현재입니다.
|===

실행:: `List<HgSigEntry> call() throws IOException, HgLockException`. 기록한 서명 줄을 반환합니다. 키링이 없으면 `IllegalStateException`, 사용할 서명 키가 없거나 커밋되지 않은 병합이거나 서명할 changeset이 없거나 `.hgsigs`가 변경됐거나 추적되지 않은 경우(force가 아니면)에는 `HgValidationException`, 알 수 없는 노드는 `HgRevisionNotFoundException`을 던집니다. 거부할 수 있는 검사는 모두 `.hgsigs`를 쓰기 전에 수행합니다.

잠금:: 명령 전체에서 작업 사본 잠금 `lockWorkingCopy()` 하나뿐입니다. 커밋(`match=.hgsigs`인 `CommitCommand`)은 store 잠금을 스스로 잡았다가 돌려줍니다. 서명, `.hgsigs` 쓰기, add는 작업 사본 잠금만 쥔 상태에서 일어납니다.

hg 원본과 다른 점:: 원본의 `hg sign --force`는 `UnboundLocalError`로 비정상 종료하지만, 여기서는 `setForce`가 동작합니다. 원본처럼 `.hgsigs`를 쓴 뒤에 실패하면 파일을 그대로 둡니다. 커밋에는 `.hgsigs`만 들어가고 다른 변경은 커밋되지 않은 채 남습니다.

[source,java]
----
List<HgSigEntry> entries = hg.sign()
    .setKeyring(keyring).setKeySpec("alice@example.org")
    .setPassphrase("secret".toCharArray()).setCommit(true).call();
----

=== SigsCommand

서명된 changeset을 최신 리비전부터, 유효한 서명자와 함께 나열합니다. `hg sigs`에 대응합니다.

[cols="2,5"]
|===
|메서드 |의미

|`setKeyring(GpgKeyring)` |검증에 쓸 키링입니다. 필수입니다.
|`setNow(Instant)` |만료를 판단하는 기준 시각입니다. 기본값은 현재입니다.
|===

실행:: `Result call() throws IOException`. `Result`는 `(List<Signed> signatures, List<String> warnings)` record이고, `Signed`는 `(int revision, String nodeHex, HgSigResult signature, String source)` record입니다. 서명은 리비전이 높은 순으로 정렬됩니다. 유효하지 않은 서명은 나열하지 않고, 그 사유를 hg가 출력했을 것과 같은 문구와 `<file>:<line>` 접두사로 `warnings`에 모읍니다(키링 자체에 대한 안내는 `GpgKeyring.getNotes()`에 남습니다). 존재하지 않는 노드의 서명은 `node does not exist` 경고가 됩니다. 서명 줄이 아닌 줄은 `IOException`(`HgSigFormatException`)입니다. 키링이 없으면 `IllegalStateException`을 던집니다. 만료는 `setNow`의 시각(기본값은 현재)을 기준으로 판단합니다. `IOException`은 저장소 읽기 실패도 포함합니다.

잠금:: 잠금을 잡지 않습니다. `refreshIfChangedOnDisk()`를 호출하고 읽기만 합니다.

hg 원본과 다른 점:: 경고를 출력하지 않고 반환하며, 형식이 잘못된 줄은 건너뛰지 않고 예외로 처리합니다.

[source,java]
----
SigsCommand.Result r = hg.sigs().setKeyring(keyring).call();
r.signatures().forEach(s -> System.out.println(s.revision() + " " + s.nodeHex()));
r.warnings().forEach(System.err::println);
----

=== SigCheckCommand

한 changeset에 기록된 모든 서명을 검증합니다. `hg sigcheck REV`에 대응합니다.

[cols="2,5"]
|===
|메서드 |의미

|`setNodeId(byte[])` |검사할 changeset입니다(20바이트 노드). 필수입니다.
|`setKeyring(GpgKeyring)` |검증에 쓸 키링입니다. 필수입니다.
|`setNow(Instant)` |만료를 판단하는 기준 시각입니다. 기본값은 현재입니다.
|===

실행:: `Result call() throws IOException`. `Result`는 `(String nodeHex, List<HgSigResult> validSignatures, List<String> warnings)` record이며 `isSigned()`를 제공합니다. `validSignatures()`가 비어 있으면 실제 hg가 `no valid signature for <short>`로 보고하는 경우입니다. 서명 파일(커밋된 것과 로컬 것)의 서명을 모두 읽어 해당 노드의 것을 골라 `setNow`의 시각(기본값은 현재)에 키링으로 각각 검증합니다. 노드나 키링이 없으면 `IllegalStateException`, 노드가 changelog에 없으면 `HgRevisionNotFoundException`(`IOException`의 하위), 저장소 읽기가 실패하면 `IOException`을 던집니다.

잠금:: 잠금을 잡지 않습니다. `refreshIfChangedOnDisk()`를 호출하고 읽기만 합니다.

hg 원본과 다른 점:: 경고를 출력하지 않고 반환합니다.

[source,java]
----
SigCheckCommand.Result r = hg.sigcheck().setNodeId(nodeBytes).setKeyring(keyring).call();
System.out.println(r.isSigned() ? "signed" : "no valid signature");
----

== 서브레포와 병합 미리보기

=== SubrepoCommand

`.hgsub`와 `.hgsubstate`를 통해 서브레포지토리를 추가, 초기화, 갱신합니다. javadoc은 "submoduleAdd / Init / Update"라고 부릅니다. 단일 hg 명령에 대응하지는 않으며, 소스 주석에 따르면 `update`와 `init`은 각 항목에 대해 `hg update -S`와 같은 일을 합니다.

[cols="2,5"]
|===
|메서드 |의미

|`setAction(String)` |`add`(`.hgsub`와 `.hgsubstate`에 항목 추가), `init` 또는 `update`(`.hgsub`에 나열된 모든 서브저장소를 `.hgsubstate`의 리비전으로 clone하거나 update) 중 하나입니다(대소문자 무시). `call()` 전에 지정해야 하며 null이면 `IllegalArgumentException`이 발생합니다.
|`setSubrepoPath(String)` |저장소 루트 기준 서브레포 경로이며 `.hgsub`에 기록됩니다. `add`에 필요합니다.
|`setSubrepoUrl(String)` |`.hgsub`에 기록되는 서브레포 원본입니다. `add`에 필요합니다.
|`setRevision(String)` |`add`가 `.hgsubstate`에 기록할 리비전 문자열입니다. `null`(기본값)이면 모두 0인 노드(0 40개)를 기록합니다. `init`과 `update`는 리비전을 `.hgsubstate`에서 읽으므로 쓰지 않습니다.
|===

실행:: `void call() throws IOException, HgLockException`. `add`는 `.hgsub`에 `path = url`을, `.hgsubstate`에 `<rev> path`를 덧붙입니다(커밋하지 않음). `init`과 `update`는 동일하게 동작합니다. `.hgsub`의 각 항목마다 `.hgsubstate`에서 고정 리비전을 찾고, 일반 hg 서브레포는 없으면 clone한 뒤 고정 리비전으로 강제 update하며, 이미 체크아웃이 있으면 고정 리비전이 로컬에 없을 때 원본에서 pull(최선 노력)하고 고정 리비전으로 강제 update합니다. hg가 아닌 기존 디렉터리는 건드리지 않습니다. `[git]`, `[svn]` 접두사 항목은 git, svn 도우미(`GitSubrepoUtil`, `SvnSubrepoUtil`)를 사용합니다. `.hgsub`가 없으면 `init`과 `update`는 조용히 반환합니다. 서브레포 파싱이나 네트워크 clone이 실패하면 `IOException`을 던지며, clone이 필요한 경로의 URL이 비어 있는 경우도 포함합니다.

잠금:: 이 클래스는 스스로 잠금을 잡지 않습니다(`lockWorkingCopy`, `lockStore` 호출 없음). 안쪽에서 호출하는 clone, pull, `UpdateCommand`가 잡는 잠금은 이 클래스에 설명되어 있지 않습니다.

hg 원본과 다른 점:: 적혀 있지 않습니다.

[source,java]
----
hg.subrepo().setAction("add").setSubrepoPath("libs/core")
    .setSubrepoUrl("https://example.org/core").call();
hg.subrepo().setAction("update").call();
----

=== TreeMergeCommand

작업 사본이 필요 없는 3-way 병합 계산입니다(javadoc은 JGit `ThreeWayMerger`와 같은 역할이라고 설명합니다). 두 커밋 노드를 받아 공통 조상과 파일별 병합을 changelog, manifest, filelog 저장소만으로 계산하고 병합 결과를 데이터로 반환합니다(예: pull request 병합 미리보기나, 작업 사본 없이 결과를 바로 커밋하는 서버 측 병합). 이때 디스크에 쓰거나 dirstate, 작업 디렉터리를 건드리지 않습니다. 실제 `hg merge`에 해당하는 porcelain 명령은 `MergeCommand`입니다.

[cols="2,5"]
|===
|메서드 |의미

|`setOurs(byte[])` |"ours" 커밋 노드(20바이트)입니다. 결과는 이 노드를 기준으로 표현됩니다. `call()` 전에 필요합니다.
|`setTheirs(byte[])` |"theirs" 커밋 노드(20바이트)이며 병합해 들어오는 changeset입니다. `call()` 전에 필요합니다.
|`setBase(byte[])` |공통 조상 대신 병합 기준으로 쓸 조상입니다. `graft`는 graft 대상 changeset의 부모를 씁니다. `null`이나 null 노드는 빈 조상을 뜻합니다.
|===

실행:: `TreeMergeResult call() throws IOException`. `TreeMergeResult`는 `isConflicted()`, `getConflicts()`(병합 내용에 충돌 표시가 남은 경로), `getChangedFiles()`("ours" 기준으로 최종 내용을 가진 경로), `getChangedModes()`(경로별 POSIX 모드: 0644, 0755, 0120000), `getRemovedFiles()`를 제공합니다. 결과는 null이 아닙니다. ours, theirs, 지정한 base가 changelog에 없으면 `HgRevisionNotFoundException`(`IOException`의 하위), 저장소 읽기가 실패하면 `IOException`을 던집니다.

잠금:: 없습니다. changelog, manifest, filelog를 읽기만 하며 `MergeCommand.call()`은 호출하지 않고, 이미 검증된 LCA 및 criss-cross 기준 해석과 파일별 `Merge3` 로직만 재사용합니다.

hg 원본과 다른 점:: 작업 사본 병합이 아니라 계산입니다. 내용 병합이 일어난 경로의 모드는 양쪽에 있으면 "ours"에서 가져오며, 이는 rebase 병합 로직의 관례를 따른 것입니다.

[source,java]
----
TreeMergeCommand.TreeMergeResult r = hg.treeMerge().setOurs(a).setTheirs(b).call();
if (r.isConflicted()) System.out.println(r.getConflicts());
r.getChangedFiles().forEach((path, bytes) -> apply(path, bytes));
----

== 파사드, 훅, 예외

=== Hg (파사드)

`Hg`는 JGit의 `Git`과 비슷한 porcelain 진입점이며 `AutoCloseable`을 구현합니다. javadoc에 따르면 인스턴스는 동시 읽기와 쓰기에 스레드 안전하고, `runTransaction`은 연속된 작업(예: status 다음 commit)에 스레드와 프로세스 수준의 원자성을 제공합니다. 각 명령 팩토리는 저장소에 묶인 새로운, 설정되지 않은 명령 객체를 반환합니다.

[cols="2,5"]
|===
|메서드 |의미

|`static Hg open(String path)` / `static Hg open(File directory)` |기존 저장소를 엽니다. `.hg/requires`와 `.hg/store/requires` 모두의 요구 사항을 지원 목록과 대조해 검증합니다. 저장소를 찾지 못하거나 유효하지 않으면 `IOException`을 던지며, `.hg`가 없으면 `HgRepositoryNotFoundException`입니다.
|`static Hg wrap(HgRepository)` |기존 저장소 핸들을 감쌉니다. null이면 `IllegalArgumentException`입니다.
|`static InitCommand init()` |저장소를 초기화하는 명령입니다.
|`static CloneCommand cloneRepository()` |저장소를 clone하는 명령입니다.
|`static NarrowCloneCommand narrowClone()` |경로 집합을 좁힌 narrow clone을 만드는 명령입니다. 기존 저장소에 묶이지 않습니다.
|`Hg registerHook(HgHookType, HgHook)` |단계별 Java 훅을 등록하고(한 단계에 여러 개면 순서대로 유지) 연쇄 호출을 위해 자기 자신을 반환합니다. type이나 hook이 null이면 무시합니다.
|`List<HgHook> getHooks(HgHookType)` |해당 단계에 등록된 훅입니다.
|`void runTransaction(Runnable) throws Exception` |`lockWorkingCopy()`, `lockStore()`를 이 순서로 쥔 채 작업을 실행하고(배타적이므로 그 사이에 다른 쓰기가 끼어들지 못함) 끝나면 둘 다 풉니다. 잠금 실패와 작업이 던진 예외는 그대로 전파됩니다.
|`HgRepository getRepository()` |감싼 저장소 핸들이며 null이 아닙니다.
|`HgRcConfig config()` |Mercurial의 우선순위 순서로 읽은 설정입니다. 시스템 hgrc(`/etc/mercurial/hgrc`), 사용자 hgrc(`~/.hgrc` 또는 `~/mercurial.ini`), 저장소 `.hg/hgrc` 순입니다.
|`List<byte[]> clonebundle(String url) throws IOException, HgLockException` |clone bundle을 평범한 HTTP(S) GET으로 내려받아 적용하고(`ClonebundlesCommand`) 가져온 커밋을 반환합니다. 여기서 실패해도 일반 pull로 조용히 대체하지 않습니다.
|`SparseConfig sparseConfig(int changelogRev)` |`.hg/sparse` 규칙(해당 리비전에서 추적되는 `%include` 프로파일 포함)을 `sparse.patternsforrev`처럼 include/exclude 패턴 집합으로 해석합니다.
|`getDiff(int, int)` / `getDiff(NodeId, NodeId)` |두 리비전 사이의 diff 항목입니다.
|`getTree(int)` / `getTree(NodeId)` |리비전의 파일 트리입니다.
|`walkManifest(String)`, `walkWorkingDir()`, `walkTree()` |새 순회기입니다. 리비전의 매니페스트 순회기(`ManifestWalk`), 작업 디렉터리 파일 순회기(`WorkingDirWalk`), 여러 트리를 병렬로 정렬 순회하는 `TreeWalk`입니다.
|`void rollback()` |작업 디렉터리 잠금과 저장소 잠금을 잡고 `RollbackCommand`(`hg rollback`)를 실행합니다. undo 정보를 읽거나 적용하지 못하면 `IOException`, 잠금을 잡지 못하면 `HgLockException`, 롤백 정보가 없으면 `IllegalStateException`을 던집니다.
|`close()` |파사드를 닫습니다.
|===

명령 팩토리(저장소에 묶인 새 명령을 반환하며, 훅이 표시된 것은 등록된 훅도 붙입니다)는 다음과 같습니다. `add()`, `commit()`(PRE_COMMIT, POST_COMMIT), `status()`, `log()`, `branch()`, `sign()`, `sigs()`, `sigcheck()`, `tag()`(PRE_TAG, POST_TAG), `bookmark()`, `merge()`(PRE_MERGE, POST_MERGE), `pull()`, `fetch()`, `worktree()`, `shelve()`, `rebase()`(PRE_REBASE, POST_REBASE), `update()`(PRE_UPDATE, POST_UPDATE), `push()`(PRE_PUSH, POST_PUSH), `cat()`, `revert()`, `remove()`, `diff()`, `tree()`, `rename()`, `annotate()`, `resolve()`, `amend()`, `bisect()`, `grep()`, `histedit()`, `export()`, `importPatch()`, `graft()`(POST_GRAFT), `purge()`, `archive()`, `gc()`, `subrepo()`, `incoming()`, `outgoing()`, `describe()`, `phase()`, `revset()`, `heads()`, `identify()`, `strip()`, `verify()`, `root()`, `tip()`, `parents()`, `summary()`, `forget()`, `addremove()`, `backout()`, `unbundle()`, `branches()`, `treeMerge()`, `censor()`, `tags()`, `paths()`, `files()`, `locate()`, `manifest()`, `copy()`, `bundle()`, `recover()`. `Hg`에는 `AdminVerifyCommand`, `NarrowServerAdmin`, `ChainsawUpdateCommand`용 팩토리가 없으므로 직접 생성합니다.

=== HgHook과 HgHookType

`HgHook`은 `@FunctionalInterface`이며 `boolean run(Map<String, Object> context) throws IOException`을 가집니다. true를 반환하면 작업을 허용하고, false를 반환하면 작업을 막고 예외를 던져 트랜잭션을 중단합니다. I/O 오류나 훅 실행 실패이면 `IOException`을 던질 수 있습니다. javadoc은 컨텍스트 키의 예로 `author`, `message`, `commitNode`, `repository`를 들지만 실제로 넘기는 키는 명령마다 다릅니다. `CommitCommand`의 pre-commit 컨텍스트에는 `author`, `message`, `repository`가 들어 있으며, false이면 `HgValidationException("Pre-commit hook execution rejected the commit txn")`을 던집니다.

다른 명령의 컨텍스트 키와 실패 동작은 javadoc과 코드 기준으로 다음과 같습니다. `PushCommand`는 pre 훅에 `destinationUrl`, `repository`를 넘기고(false이면 `HgValidationException`), post 훅에 `destinationUrl`, `response`, `repository`를 넘깁니다(반환값 무시, 예외 삼킴, 잠금을 푼 뒤 changeset을 보낸 경우에만 실행). `RebaseCommand`는 pre 훅에 `repository`, `sourceNode`, `targetNode`를 넘기고(false이면 `HgValidationException`, 메시지 `Rebase rejected by PRE_REBASE hook`), post 훅에 `sourceNode`, `targetNode`, `rebasedTipNode`(마지막 새 변경 집합의 16진 값, 없으면 null), `repository`를 넘깁니다(반환값 무시, 예외는 기록하고 삼킴). `GraftCommand`는 post 훅에 `sourceRevision`, `graftedNode`, `repository`를 넘깁니다(반환값 무시, 예외는 경고로 기록하므로 post-graft 훅은 graft를 중단할 수 없음). `TagCommand`는 `repository`, `tag`, `node`를 넘기며, pre 훅이 false이면 `HgValidationException`(`Tag creation rejected by PRE_TAG hook`)이고 post 훅의 예외는 전파됩니다.

등록은 `hg.registerHook(HgHookType.PRE_COMMIT, ctx -> ...)`로 합니다. 훅은 해당 명령을 `Hg`의 팩토리 메서드로 만들 때 명령에 붙습니다. `new XCommand(repo)`로 직접 만든 명령은 등록된 훅을 받지 않습니다. 같은 패키지의 `ProcessHook`은 외부 프로세스를 실행하고 컨텍스트 항목을 `HG_<KEY>` 환경 변수로 넘기는 `HgHook`입니다. 명령줄은 따옴표로 묶이지 않은 공백으로 나뉩니다(작은따옴표나 큰따옴표는 단어를 묶음. 셸을 쓰지 않으므로 확장이나 리다이렉션은 없음). 생성자는 명령 문자열이나, 목록과 선택적 작업 디렉터리를 받으며, 작업 디렉터리가 없으면 컨텍스트의 `repository` 항목의 디렉터리를, 그것도 없으면 JVM의 현재 디렉터리를 씁니다. null, 공백, 빈 명령은 아무것도 실행하지 않고 허용합니다. 종료 코드 0이면 작업을 허용하고, 그 밖의 종료 코드는 경고를 기록하고 거부합니다(false 반환).

=== 예외 (패키지 io.github.search5.hg4j.errors)

[cols="2,5"]
|===
|클래스와 상위 클래스 |던져지는 경우(javadoc과 코드 기준)와 호출하는 쪽의 조치

|`HgException` extends `Exception`
|Mercurial 도메인과 동작 예외의 체크 예외 기반 클래스입니다(생성자는 메시지와 선택적 원인을 받음). 직접 던져지지는 않습니다. `HgLockException`과 `HgMergeConflictException`을 함께 처리하려는 경우에만 잡습니다.

|`HgLockException` extends `HgException`
|저장소 잠금을 얻지 못했거나 잠금 경합이 있을 때 던집니다(잠금을 푸는 데 실패한 경우도 포함). 메시지는 `Failed to acquire lock '<name>': ...`이며 `getLockName()`이 잠금 이름(예: `store.lock`, `wlock`)을 줍니다. 기다리는 명령은 저장소의 push 잠금 대기 시간을 쓰며 `0`이면 즉시 실패합니다. 호출하는 쪽의 조치: 나중에 재시도하거나 다른 프로세스를 찾아 멈춥니다. 다른 프로세스가 없다고 확신하기 전에는 잠금 파일을 지우지 않습니다(`ChainsawUpdateCommand`는 의도적으로 잠금을 깹니다).

|`HgAbandonedTransactionException` extends `HgLockException`
|중단된 트랜잭션(`store/journal`)이 복구를 기다릴 때 던집니다. 메시지는 `abandoned transaction found`, 안내는 `run 'hg recover' to clean up transaction`, 잠금 이름은 `lock`입니다. `HgRepository.lockStore(int)`가 journal이 있고 잠금이 재진입이 아닐 때 던집니다. 암묵적으로 복구하지 않습니다. 호출하는 쪽의 조치: `RecoverCommand`(`hg.recover().call()`)를 실행한 뒤 재시도합니다. `lockStoreWithoutRecovery`는 이 예외를 일으키지 않으며, 그래서 `VerifyCommand`, `RecoverCommand`, `GcCommand`가 그것을 씁니다.

|`HgMergeConflictException` extends `HgException`
|3-way 병합에서 해결되지 않은 충돌이 남았을 때 던집니다. `MergeCommand`, `RebaseCommand`의 cherry-pick 경로(`ShelveCommand`의 unshelve 포함), `GraftCommand`, `BackoutCommand`가 해당합니다. `getConflictPath()`는 첫 충돌 파일, `getConflictPaths()`는 모든 충돌 파일입니다. 충돌 표시는 작업 파일에, 기록은 `.hg/merge/state2`에 남습니다. 호출하는 쪽의 조치: 파일을 해결한(예: `ResolveCommand`) 뒤 계속하거나(`continueRebase()`, `continueGraft()`, `unshelveContinue()`) 취소합니다(`abort()`, `unshelveAbort()`). `BackoutCommand` 충돌 뒤에는 아무것도 커밋되지 않았으므로 해결한 뒤 평소처럼 커밋합니다.

|`HgValidationException` extends `IOException`
|저장소 상태나 작업 디렉터리에 대한 선행 조건 또는 무결성 검사가 실패했을 때 던집니다. 명령이 "거부"를 알리는 일반적인 신호이며, 예를 들어 `uncommitted changes`, `outstanding uncommitted merge`, `no rebase in progress`, `empty revision set`, 지원하지 않는 옵션, false를 반환한 훅이 있습니다. 호출하는 쪽의 조치: 메시지를 읽고 상태를 고친 뒤(변경을 커밋하거나 되돌리고, 병합을 해결하고, 인자를 바로잡고) 다시 호출합니다. 작업이 시작되기 전에 던져졌다면 아무것도 바뀌지 않았습니다.

|`HgPushRacedException` extends `HgValidationException`
|서버 측 push/unbundle 적용(로컬 `file://` 피어와 bundle2 push)에서 클라이언트가 계산한 뒤 저장소 잠금을 얻기 전에 저장소의 head, 북마크, phase가 바뀌어 동시 push 경합에서 졌을 때 던집니다. 메시지는 `remote repository changed while pushing - please try again`입니다(북마크와 phase는 세부 내용이 붙음). 아무것도 적용되지 않았습니다. 호출하는 쪽의 조치: 타입으로 잡아 새 변경을 pull한 뒤 push를 재시도합니다.

|`HgCorruptDataException` extends `IOException`
|데이터 무결성 실패입니다. revlog 체크섬 불일치, 손상된 delta 복원이나 인덱스, 읽을 수 없는 dirstate, sidedata, 폐기 마커, LFS 포인터 데이터가 해당합니다. `UnbundleCommand`는 알 수 없는 bundle 헤더나 지원하지 않는 bundle1 압축에도 이 예외를 던집니다. 호출하는 쪽의 조치: 무작정 재시도하지 않습니다. `VerifyCommand`를 실행하고 백업에서 복원하거나 다시 clone합니다. 쓰기가 중단된 경우에는 `RecoverCommand`를 실행합니다.

|`HgCensoredContentException` extends `IOException`
|`Revlog`로 censor된 파일 리비전의 내용을 읽을 때 tombstone을 조용히 돌려주는 대신 던집니다(`error.CensoredNodeError`에 대응). `getTombstone()`이 tombstone 바이트를 줍니다(null일 수 있음). 호출하는 쪽의 조치: 내용이 의도적으로 제거된 것으로 취급합니다. 원본 바이트가 정말 필요하면 tombstone 문구를 쓰거나 revlog의 `getRawRevisionContent`를 사용합니다.

|`HgHookRejectedException` extends `IOException`
|훅이 작업을 거부했을 때 던집니다. 로컬 피어 적용에서 `pretxnchangegroup` 훅이 실패하면 던져지며(메시지 `pretxnchangegroup hook failed`), 서버 코드가 이를 거부 응답으로 바꿉니다. 변경이 이루어진 뒤에 훅이 실행되어 변경이 되돌려졌으면 `isRolledBack()`이 true이고, 아무것도 바뀌기 전에 거부했으면 false입니다. 호출하는 쪽의 조치: `isRolledBack()`이 true이면 저장소는 이전 상태로 돌아가 있으므로, 훅이 문제 삼은 내용을 고친 뒤 재시도합니다.

|`HgRepositoryNotFoundException` extends `IOException`
|잘못된 경로나 손상 때문에 저장소(또는 보관본이나 filelog 같은 필요한 파일)를 찾을 수 없을 때 던집니다. `getPath()`가 경로를 줍니다. `Hg.open`, `InitCommand`(저장소 디렉터리를 만들 수 없을 때), `ShelveCommand`(보관 파일이 없을 때), `CensorCommand`(filelog가 없는 파일)가 던집니다. 호출하는 쪽의 조치: 경로와 `.hg` 존재 여부를 확인하거나 `Hg.init()`으로 저장소를 만듭니다.

|`HgRevisionNotFoundException` extends `IOException`
|노드 ID나 리비전 번호로 리비전을 찾지 못했을 때 던집니다(메시지에 40자리 16진 노드나 리비전 번호가 들어 있음). 리비전을 해석하는 명령(예: `CensorCommand`, `SigCheckCommand`, `TreeMergeCommand`, `SignCommand`)이 던집니다. 호출하는 쪽의 조치: 식별자를 확인합니다. 해당 changeset이 다른 저장소에 있거나, strip되었거나, 아직 pull되지 않았을 수 있습니다.

|`HgTransportException` extends `IOException`
|HTTP/SSH 전송 계층의 네트워크 및 wire 프로토콜 오류의 기반 클래스입니다. 메시지는 `Transport error for '<url>': ...`이고 `getRemoteUrl()`이 URL을 줍니다. `HgRemoteClient`는 URL 형식이 잘못되었을 때 이 예외를 직접 던집니다. 호출하는 쪽의 조치: 주소와 네트워크를 확인합니다. 모든 전송 실패를 처리하려면 기반 클래스를 잡습니다.

|`HgAuthException` extends `HgTransportException`
|SSH 또는 HTTP 자격 증명 인증에 실패했을 때 던집니다. HTTP 401 또는 403 응답(사용자 이름이 없으면 `anonymous`)이나 SSH 인증 실패입니다. `getUsername()`이 실패한 사용자 이름을 줍니다. 호출하는 쪽의 조치: 올바른 자격 증명을 제공하고(주소, `[auth]` 섹션, `PullCommand`/`FetchCommand`의 `setCredentialsProvider`) 재시도합니다.

|`HgProtocolException` extends `HgTransportException`
|wire 프로토콜 오류입니다. capability 협상 실패, 프로토콜이 허용하지 않는 서버 응답, clone bundle 다운로드가 200이 아닌 응답을 받은 경우(`ClonebundlesCommand`)입니다. 호출하는 쪽의 조치: 서버가 쓰는 프로토콜 버전과 capability(예: SSH v2 스위치)를 지원하는지, URL이 Mercurial 서버를 가리키는지 확인합니다. 같은 요청을 재시도하면 대개 같은 결과가 나옵니다.
|===

참고로 `HgException`과 `HgLockException`은 `IOException`을 상속하지 않는 체크 예외이고, 나머지 대부분은 `IOException`을 상속합니다.
