// Maintenance, signing, subrepo and merge-preview commands; facade, hooks and exceptions.
// All classes are in io.github.search5.hg4j.api unless noted. Everything below is taken from the source.

== Maintenance and integrity commands

=== VerifyCommand

Checks the integrity of the repository store. Corresponds to `hg verify`. The javadoc calls it a "simplified verifier": it checks node id hash consistency of the changelog, the manifest, treemanifest submanifests under `meta/` and every filelog, and it does not cross-check changelog, manifest and filelog linkage.

[cols="2,5"]
|===
|Method |Meaning

|`VerifyCommand(HgRepository)` |Constructor. A null repository raises `IllegalArgumentException`.
|`setSkipLfs(boolean)` |`hg verify --no-lfs`: do not read (so do not fetch) an LFS blob that is not stored locally. The config `verify.skipflags` with the EXTSTORED bit (0x2000) has the same effect.
|===

Execution:: `List<String> call() throws HgLockException`. Returns the error messages; an empty list means the checks found nothing. Read failures inside the check are reported as the message `critical repository read failure: ...` and are not thrown. A failure while releasing the lock is rethrown as `HgLockException`. A repository without `00changelog.i` counts as an empty changelog (0 revisions), as in real hg. A missing `00manifest.i` is an error only when the changelog has revisions. Filelogs are discovered from `fncache` plus a walk of `data/`; an `fncache` entry whose index file is missing is reported.

Locking:: The store lock only, via `lockStoreWithoutRecovery`, held around the whole check ("Like real hg (verify.verify)"). No working copy lock. dirstate is not touched.

Differences from hg:: Simplified verifier as described above (no linkage cross-checks). Otherwise not stated in the source.

[source,java]
----
try (Hg hg = Hg.open("/path/to/repo")) {
    List<String> errors = hg.verify().setSkipLfs(true).call();
    if (!errors.isEmpty()) errors.forEach(System.err::println);
}
----

=== RecoverCommand

Rolls back an interrupted transaction (a leftover `.hg/store/journal`). Corresponds to `hg recover` (and `hg recover --verify`).

[cols="2,5"]
|===
|Method |Meaning

|`RecoverCommand(HgRepository)` |Constructor. A null repository raises `IllegalArgumentException`.
|`setVerify(boolean)` |`hg recover --verify`: only when an interrupted transaction was found and rolled back, additionally run `VerifyCommand` and report its errors on the result.
|===

Execution:: `RecoverResult call() throws HgLockException`. The result has `wasInterrupted()` (a journal was found; false is real hg's "no interrupted transaction available"), `isSuccess()` (nothing to recover, or rolled back; false means the rollback could not complete and the journal is kept for a retry) and `getVerifyErrors()` (null unless verify ran; an empty list means verify found nothing). "Nothing to recover" is returned as a result, not thrown.

Locking:: The store lock only, via `lockStoreWithoutRecovery` (the lock does not recover by itself). No working copy lock is taken. The rollback is delegated to `HgRepository.checkAndPerformAutoRollback()`, which restores the store files from the journal and never touches the dirstate (the code notes that recovering a transaction does not change it, because the dirstate is written after the transaction). The lock wait uses the repository's push lock timeout. When `setVerify(true)` applies, `VerifyCommand.call()` runs under the same held lock. Without a journal nothing is done.

Differences from hg:: Returns a `RecoverResult` instead of an exit code or message, and "nothing to recover" (real hg: `no interrupted transaction available`, exit 1) is a normal result, not an error, so a library caller can run it as a health check before opening.

[source,java]
----
RecoverCommand.RecoverResult r = hg.recover().setVerify(true).call();
if (r.wasInterrupted() && !r.isSuccess()) {
    System.err.println("journal kept for retry");
}
----

=== RollbackCommand

Undoes the last transaction using the `undo*` files. Corresponds to `hg rollback`.

[cols="2,5"]
|===
|Method |Meaning

|`RollbackCommand(HgRepository)` |Constructor. There are no setters.
|===

Execution:: `void call() throws IOException, HgLockException`. Also reachable as `Hg.rollback()` (same throws). Takes the working copy lock and the store lock, waiting up to the repository's push lock timeout. Throws `IllegalStateException("No rollback information available (undo file not found)")` when `store/undo` does not exist, `IOException` when restoring the files fails, and `HgLockException` when a lock cannot be acquired within the timeout. Steps: (1) read `undo` and truncate or delete store files (`trunc` lines truncate only, `backup` lines restore full file bytes for v2 docket revlogs, plain lines truncate to the recorded size or delete on size 0); (2) restore `.hg/dirstate` from `.hg/undo.backup.dirstate` (or delete `dirstate` when no backup exists), and restore the dirstate-v2 data file from `.hg/undo.backup.dirstate.data` when the docket's uid file is missing; (3) restore `.hg/bookmarks` from `.hg/undo.backup.bookmarks` (or delete it) and delete `.hg/bookmarks.current`; (4) in a `finally`, delete all `undo*` info files and the consumed docket backups, and clear the revlog cache.

Locking:: `lockWorkingCopy(timeout)` first, then `lockStore(timeout)` (the version that, per `HgRepository.lockStore`, refuses with `HgAbandonedTransactionException` when a journal exists and the lock is not re-entrant), both taken before the first read and released at the end. Rollback does modify dirstate and bookmarks.

Differences from hg:: Not stated beyond the conformance note in the class javadoc to the `undo.*` layout.

[source,java]
----
hg.rollback();
// or
new RollbackCommand(hg.getRepository()).call();
----

=== GcCommand

Store compaction and cleanup. No exact hg command; the source says the nearest real operations are `debugupgraderepo` and `debugrebuildfncache`.

[cols="2,5"]
|===
|Method |Meaning

|`GcCommand(HgRepository)` |Constructor. There are no setters.
|===

Execution:: `String call() throws IOException, HgLockException`. Returns a summary string of the form `GC / Compaction complete: defragmented and re-delta optimized N store revlogs, cleaned M orphaned temp files.` Throws `IOException` when the store directory does not exist (checked first, because taking a lock would create it). Steps: clear the revlog cache; delete `*.backup`, `*.tmp` and `journal` files in the store root; rewrite the changelog, the manifest and every `.i` revlog under `data/` and `meta/` revision by revision into temp files and swap them in atomically (empty revlogs and v2/docket revlogs are skipped and left untouched); rebuild `fncache` with atomic IO (entries for `data/` and `meta/` revlogs only, plus `.d` entries for split revlogs), skipped for `fileindex-v1` repositories or when nothing was found; call `System.gc()`.

Locking:: `lockWorkingCopy(timeout)` first, then `lockStoreWithoutRecovery(timeout)`, because the command removes leftovers including a stale journal itself and counts them.

Differences from hg:: No direct counterpart. v2/docket revlogs (`changelog-v2`, `general-v2`) are never rewritten because the source says real hg has no compaction for them and rewriting would be destructive.

[source,java]
----
String summary = hg.gc().call();
System.out.println(summary);
----

=== AdminVerifyCommand

Runs named repository checks. Corresponds to `hg admin::verify` (`admin/verify.py`). Mercurial 7.2 registers one check here, `working-copy.dirstate` (alias `dirstate`), which compares the dirstate with the manifests of its parents.

[cols="2,5"]
|===
|Method |Meaning

|`AdminVerifyCommand(HgRepository)` |Constructor.
|`addCheck(String)` |`-c/--check`: a check to run. A name is a qualified name, an alias, a prefix of a qualified name (`working-copy` runs everything below it) or `full`. With none, the call fails.
|`addOption(String)` |`-o/--option`: `check:option=value`. The check has to accept the option; the only registered check accepts none.
|`getOutput()` |The lines `ui.status` printed.
|`getWarnings()` |The lines `ui.warn` printed: findings, and the warning `abandoned transaction found - run hg recover` when a journal exists.
|===

Execution:: `Map<String, Integer> call() throws IOException`. Returns the number of errors per check (qualified name) for each check that found some. Throws `HgValidationException` (an `IOException`) for an unknown check, an invalid option, an option for an unselected check, an option the check does not have, and when no check was selected (`` `checks` required ``).

Locking:: None. The class javadoc says "Nothing is locked: it only reads."

Differences from hg:: Not stated beyond the single registered check.

[source,java]
----
AdminVerifyCommand v = new AdminVerifyCommand(hg.getRepository()).addCheck("dirstate");
Map<String, Integer> found = v.call();
v.getWarnings().forEach(System.err::print);
----

=== NarrowServerAdmin

Administration of the shards and shapes of a server repository. Corresponds to `hg admin::narrow-server` and `admin::narrow-client` (`--store-fingerprint`). The class is final and has no `call()`; each option is its own method. The source points to `llm-wiki/concepts/store-shapes.md` sections 10 and 11 for the analysis.

[cols="2,5"]
|===
|Method |Meaning

|`NarrowServerAdmin(HgRepository)` |Constructor.
|`getWarnings()` |What the last call warned about (`ui.warn`), for example a store shapes update in progress.
|`shapeFingerprints()` |`--shape-fingerprints`: `<fingerprint> <names>` for every shape.
|`storeShardsListing()` |`--store-shards`: the id of every shard, then `read-write-access=a,b` when it has some.
|`shapePatterns(String names)` |`--shape-patterns NAMES`: `inc:/path` and `exc:/path` lines in zero path order.
|`shapeNarrowPatterns(String names)` |`--shape-narrow-patterns NAMES`: the legacy `[include]` and `[exclude]` sections without the root.
|`shapeFiles(String names, boolean hiddenOnly)` |`--shape-files` / `--shape-files-hidden`: sorted filelogs of the store covered by the shape; with `hiddenOnly`, only those not in the working copy.
|`shapeUpdate(byte[] newContents, UpdateOptions options)` |`--shape-update`: replaces the `server-shapes` file after validation. A header comment is prepended when missing.
|`shapeClearPrevious()` |`--shape-clear-previous`: removes the saved previous configs; returns `cleared N saved server-shapes`.
|`static storeFingerprint(Set<String> includes, Set<String> excludes)` |`admin::narrow-client --store-fingerprint`: the fingerprint of a narrow clone's store narrowspec, with a trailing newline.
|`UpdateOptions(overrideReshapeAndReshardCheck, overrideFingerprintChangeCheck, overrideSavedConfigsCheck)` |Record of the three `override-*` flags of `--shape-update`; `UpdateOptions.strict()` has all false.
|===

Execution:: Listing methods return `List<String>` and throw `IOException`. `shapeUpdate` returns void and throws `IOException, HgLockException`. `shapeClearPrevious` returns `String` and throws `IOException, HgLockException`. Every instance method first throws `HgValidationException("repo is narrowed, this is a server command")` when `narrowhg-experimental` is in `.hg/requires` or `store/requires`. An unknown shape name gives `HgValidationException("shape '...' not found")`. `shapeUpdate` validation (`HgValidationException`) refuses redefining the fingerprint of an existing shape, reshaping and resharding in one update, and reshaping while previous configs are still saved, each unless its override flag is set.

Locking:: Listing methods take no lock and only warn when an update is in progress. `shapeUpdate`: the store shapes lock without waiting (`lockStoreShapes(0)`), read the old config, parse and validate the new one (a bad document aborts before anything is written), then the store lock (`lockStoreWithoutRecovery`) only for the write, saving the old config first when shards changed, then an atomic write. `shapeClearPrevious`: shapes lock then store lock together. No working copy lock.

Differences from hg:: Not stated.

[source,java]
----
NarrowServerAdmin admin = new NarrowServerAdmin(hg.getRepository());
admin.shapeFingerprints().forEach(System.out::println);
admin.shapeUpdate(Files.readAllBytes(Path.of("server-shapes")), NarrowServerAdmin.UpdateOptions.strict());
----

=== ChainsawUpdateCommand

Pulls and updates to a revision no matter what. Corresponds to `hg admin::chainsaw-update` (`mercurial/admin/chainsaw.py`). The javadoc marks it DANGEROUS: a non-repository directory at the destination is removed, locks left by anybody are broken, local changes and unknown files are thrown away. Intended for unattended use with exclusive access.

[cols="2,5"]
|===
|Method |Meaning

|`setRevision(String)` |`--rev`: the target revision. Required.
|`setSource(String)` |`--source`: where to pull from. Required.
|`setDestination(String)` |`--dest`: the repository to update; it is cloned (created) when it does not exist. Required.
|`setPurgeUnknown(boolean)` |`--purge-unknown`, default on.
|`setPurgeIgnored(boolean)` |`--purge-ignored`, default on.
|`setInitialCloneMinimal(boolean)` |`--initial-clone-minimal`: pull only the revision when the repository is created (so no clone bundle is used).
|`getMessages()` |What the command told the user, line by line as hg prints it.
|===

Execution:: `void call() throws IOException, HgLockException`. Throws `HgValidationException` when revision, source or destination is empty, `IOException` when any step fails, and `HgLockException` when the locks cannot be taken after the old ones were broken. If `<dest>/.hg` exists the repository is loaded; otherwise whatever is at the destination is deleted, a repository is created with `Hg.init()` and the repository is pulled in full unless `setInitialCloneMinimal(true)`. Then: break the locks, recover, pull, purge, force update.

Locking:: As in the original, in this order: the lock files `store/lock` and `.hg/wlock` are deleted without taking anything (messages `had to break store lock` and `had to break working copy lock`); then `lockWorkingCopy()` and `lockStoreWithoutRecovery(timeout)` are taken together for recovery (`RecoverCommand`), pull, purge (`PurgeCommand` with directories, files = purge unknown, ignored = purge ignored) and update (`UpdateCommand` with force). The pull and the update take the same locks again (re-entrant); purge takes none of its own.

Differences from hg:: Not stated beyond the danger notice above.

[source,java]
----
ChainsawUpdateCommand c = new ChainsawUpdateCommand()
    .setSource("https://example.org/repo").setDestination("/srv/checkout").setRevision("default");
c.call();
c.getMessages().forEach(System.out::print);
----

== Signing commands

These use the `gpg` extension format (`hgext/gpg.py`). All three need a `GpgKeyring` (set with `setKeyring`).

=== SignCommand

Signs changesets with a GPG key. Corresponds to `hg sign`. The signature is recorded in `.hgsigs` (committed) or, with `setLocal`, in `.hg/localsigs` (never committed). The format and signed text are those of the `gpg` extension, so `hg sigcheck` accepts what is written.

[cols="2,5"]
|===
|Method |Meaning

|`setNodeId(byte[])` |The changeset to sign (20-byte node). Default: the working directory's parent.
|`setKeyring(GpgKeyring)` |The keys to sign with; must contain a secret key (`GpgKeyring.withSecretKeys`). Required.
|`setKeySpec(String)` |`hg sign --key`: part of a user id, or a key id / fingerprint (suffix).
|`setPassphrase(char[])` |The key's passphrase; null or empty for an unprotected key.
|`setLocal(boolean)` |`--local`: write `.hg/localsigs`, which is not versioned and never committed.
|`setCommit(boolean)` |`--no-commit` is `setCommit(false)`: write and track `.hgsigs` but do not commit. Default true.
|`setForce(boolean)` |`--force`: sign even though `.hgsigs` has uncommitted changes.
|`setMessage(String)` |The commit message; default is one line `Added signature for changeset <short>` per signed changeset.
|`setAuthor(String)` |Commit author of the `.hgsigs` commit, normally `Name <email>`. Default `hg4j <hg4j@google.com>`. Unused with `setLocal` or when `setCommit(false)`.
|`setSigningTime(Instant)` |The signature creation time; default now.
|===

Execution:: `List<HgSigEntry> call() throws IOException, HgLockException`; returns the signature lines that were recorded. Throws `IllegalStateException` without a keyring; `HgValidationException` for no usable signing key, an uncommitted merge, a repository with no changeset, or a changed or untracked `.hgsigs` (unless forced); `HgRevisionNotFoundException` for an unknown node. All checks that can refuse run before `.hgsigs` is written.

Locking:: The working copy lock only, `lockWorkingCopy()`, for the whole command. The commit (`CommitCommand` with `match=.hgsigs`) takes the store lock itself and releases it. Signing, the write of `.hgsigs` and the add happen under the working copy lock alone.

Differences from hg:: `hg sign --force` crashes in the original with `UnboundLocalError`; `setForce` works here. Like the original, a failure after `.hgsigs` was written leaves the file as it is. The commit holds `.hgsigs` only; other changes stay uncommitted.

[source,java]
----
List<HgSigEntry> entries = hg.sign()
    .setKeyring(keyring).setKeySpec("alice@example.org")
    .setPassphrase("secret".toCharArray()).setCommit(true).call();
----

=== SigsCommand

Lists signed changesets, newest revision first, with each valid signer. Corresponds to `hg sigs`.

[cols="2,5"]
|===
|Method |Meaning

|`setKeyring(GpgKeyring)` |The keyring to verify against. Required.
|`setNow(Instant)` |The time expiry is judged against; default now.
|===

Execution:: `Result call() throws IOException`. `Result` is a record `(List<Signed> signatures, List<String> warnings)`; `Signed` is a record `(int revision, String nodeHex, HgSigResult signature, String source)`. Signatures are sorted highest revision first. Invalid signatures are not listed; their reasons are collected in `warnings` with the same wording and the `<file>:<line>` prefix hg would have printed (keyring notes stay in `GpgKeyring.getNotes()`). A signature of a node that does not exist gives the warning `node does not exist`. A line that is not a signature line at all is an `IOException` (`HgSigFormatException`). Throws `IllegalStateException` without a keyring. Expiry is judged at the time of `setNow` (default now). `IOException` also covers a failure to read the repository.

Locking:: None taken; it calls `refreshIfChangedOnDisk()` and reads.

Differences from hg:: Warnings are returned instead of printed; a malformed line is an exception instead of being skipped.

[source,java]
----
SigsCommand.Result r = hg.sigs().setKeyring(keyring).call();
r.signatures().forEach(s -> System.out.println(s.revision() + " " + s.nodeHex()));
r.warnings().forEach(System.err::println);
----

=== SigCheckCommand

Verifies every signature recorded for one changeset. Corresponds to `hg sigcheck REV`.

[cols="2,5"]
|===
|Method |Meaning

|`setNodeId(byte[])` |The changeset to check (20-byte node). Required.
|`setKeyring(GpgKeyring)` |The keyring to verify against. Required.
|`setNow(Instant)` |The time expiry is judged against; default now.
|===

Execution:: `Result call() throws IOException`. `Result` is a record `(String nodeHex, List<HgSigResult> validSignatures, List<String> warnings)` with `isSigned()`. An empty `validSignatures()` is what real hg reports as `no valid signature for <short>`. It reads every signature from the signature files (committed and local), picks those for the node and verifies each against the keyring at the time of `setNow`. Throws `IllegalStateException` when the node or keyring is missing, `HgRevisionNotFoundException` (an `IOException`) when the node is not in the changelog, and `IOException` when reading the repository fails.

Locking:: None taken; it calls `refreshIfChangedOnDisk()` and reads.

Differences from hg:: Warnings are returned instead of printed.

[source,java]
----
SigCheckCommand.Result r = hg.sigcheck().setNodeId(nodeBytes).setKeyring(keyring).call();
System.out.println(r.isSigned() ? "signed" : "no valid signature");
----

== Subrepo and merge preview

=== SubrepoCommand

Adds, initializes or updates subrepositories through `.hgsub` and `.hgsubstate`. The javadoc names it "submoduleAdd / Init / Update". No single hg command; `update` and `init` do what `hg update -S` does for each entry, per the comments in the source.

[cols="2,5"]
|===
|Method |Meaning

|`setAction(String)` |`add` (append an entry to `.hgsub` and `.hgsubstate`), or `init` or `update` (clone or update every subrepository listed in `.hgsub` to the revision in `.hgsubstate`); case-insensitive. Must be set before `call()`; null raises `IllegalArgumentException`.
|`setSubrepoPath(String)` |Subrepo path relative to the repository root, written to `.hgsub`. Required for `add`.
|`setSubrepoUrl(String)` |Subrepo source written to `.hgsub`. Required for `add`.
|`setRevision(String)` |Revision string written to `.hgsubstate` by `add`; `null` (the default) records the all-zero node (40 zeros). Not used by `init` or `update`, which read the revision from `.hgsubstate`.
|===

Execution:: `void call() throws IOException, HgLockException`. `add` appends `path = url` to `.hgsub` and `<rev> path` to `.hgsubstate` (no commit). `init` and `update` behave the same: for each `.hgsub` entry, find the pinned revision in `.hgsubstate`, then for a plain hg subrepo clone it when absent (with a forced update to the pin), or when it already is a checkout pull the source if the pin is not present locally (best effort) and force-update to the pin; an existing non-hg directory is left untouched. `[git]` and `[svn]` prefixed entries use the git and svn helpers (`GitSubrepoUtil`, `SvnSubrepoUtil`). If `.hgsub` is missing, `init` and `update` return silently. Throws `IOException` when subrepo parsing or network cloning fails, including a subrepo URL that is empty for a path that must be cloned.

Locking:: This class takes no lock itself (no `lockWorkingCopy` or `lockStore` call). Locks taken by the nested clone, pull and `UpdateCommand` calls are not described in this class.

Differences from hg:: Not stated.

[source,java]
----
hg.subrepo().setAction("add").setSubrepoPath("libs/core")
    .setSubrepoUrl("https://example.org/core").call();
hg.subrepo().setAction("update").call();
----

=== TreeMergeCommand

A working-copy-free 3-way merge computation (the javadoc says JGit `ThreeWayMerger` parity). Takes two commit nodes, computes their common ancestor and the per-file merge purely from the changelog, manifest and filelog store, and returns the merge as data (for example for a pull request merge preview, or a server-side merge that commits its result without a working copy). It does not write to disk or touch dirstate or the working directory. `MergeCommand` stays the porcelain command for real `hg merge`.

[cols="2,5"]
|===
|Method |Meaning

|`setOurs(byte[])` |The "ours" commit node (20 bytes); the result is expressed relative to it. Required before `call()`.
|`setTheirs(byte[])` |The "theirs" commit node (20 bytes), the changeset merged in. Required before `call()`.
|`setBase(byte[])` |The ancestor to merge against instead of the common ancestor; `graft` uses the parent of the grafted changeset. `null` or the null node means an empty ancestor.
|===

Execution:: `TreeMergeResult call() throws IOException`. `TreeMergeResult` has `isConflicted()`, `getConflicts()` (paths whose merged content still has conflict markers), `getChangedFiles()` (path to final content, relative to "ours"), `getChangedModes()` (path to POSIX mode: 0644, 0755, 0120000) and `getRemovedFiles()`. The result is never `null`. Throws `HgRevisionNotFoundException` (an `IOException`) when ours, theirs or a given base is not in the changelog, and `IOException` when reading the store fails.

Locking:: None. Pure reads of the changelog, manifest and filelogs; `MergeCommand.call()` is never invoked, only its already verified LCA and criss-cross base resolution and the per-file `Merge3` logic are reused.

Differences from hg:: It is a computation, not a working copy merge. A file that one side deleted and the other changed is a conflict (listed in `getConflicts()` without content in `getChangedFiles()`), as in `hg merge`. For a path merged by content, the mode is taken from "ours" when both sides have it, following the convention of the rebase merge logic.

[source,java]
----
TreeMergeCommand.TreeMergeResult r = hg.treeMerge().setOurs(a).setTheirs(b).call();
if (r.isConflicted()) System.out.println(r.getConflicts());
r.getChangedFiles().forEach((path, bytes) -> apply(path, bytes));
----

=== MergeCommitCommand

Merges two heads and commits the result as one changeset with two parents, without a working copy: `hg merge -r P2` followed by `hg commit`, for a server repository that has no checkout. The merge is computed by `TreeMergeCommand`; the new file revisions, manifest and changeset are written the way the original's `commit` writes them. A file the merge takes unchanged from the second parent keeps that parent's file revision, a file both sides changed gets a new file revision with two parents, and the changeset lists only the files that were really touched. For the same two heads, user, date and message the result is the same changeset (same node) that `hg merge` and `hg commit` create; the interop tests compare the nodes. Repositories with changeset sidedata (changelog-v2) get the changed-files sidedata, equal to what the original stores.

[cols="2,5"]
|===
|Method |Meaning

|`setP1(byte[])`, `setP1(String)` |The first parent: the head the merge is committed on (the receiving side). A node, or a revision identifier. Required.
|`setP2(byte[])`, `setP2(String)` |The second parent: the head merged in (the sending side). Required.
|`setBase(byte[])`, `setBase(String)` |The ancestor to merge against instead of the common ancestor of the parents (optional).
|`setUser(String)` |The committer as stored in the changeset. Required.
|`setMessage(String)` |The message; trailing white space of each line and empty lines at both ends are removed, as `hg commit` does. Required, not blank.
|`setDate(String)` |`"<unix seconds> <offset>"`, the offset in seconds west of UTC. Default: now, local time zone. A malformed date throws `HgValidationException`.
|`setBranch(String)` |The named branch of the merge changeset. Default: the branch of the first parent.
|`putExtra(String, String)` |An `extra` entry of the changeset. The key `branch` is refused (`IllegalArgumentException`); use `setBranch`.
|`setAllowAncestorMerge(boolean)` |Allows a merge in which one parent is an ancestor of the other, like `git merge --no-ff`. Default `false`.
|===

Execution:: `MergeCommitResult call() throws IOException, HgLockException`. `MergeCommitResult` has `isConflicted()`, `getConflicts()` (sorted paths), `getNode()` (20 bytes, `null` when conflicted) and `getNodeHex()`. A conflict is a value, not an exception, and nothing has been written then. Throws `HgValidationException` for a missing user or message, an invalid date, the same changeset on both sides, one parent being an ancestor of the other (unless allowed) and a treemanifest repository; `HgRevisionNotFoundException` when a parent or the base is not in the changelog; `HgLockException` when the store lock cannot be taken; `IOException` for store errors, after which the repository is rolled back.

Locking:: Only the store lock (`lockStore`) and a rollback transaction, no `wlock` and no dirstate, as for `GraftInMemory`. The lock is held for the whole call: the merge computation and the writes. Waits up to `[ui] timeout` for another holder.

Differences from hg:: A file one side deleted and the other changed is a conflict (the original asks the user). Copies and renames are followed: a file one side copied or renamed and the other side changed under its old name gets the change merged into the new name, and the new file revision records the copy; the interop tests compare the resulting changesets with the real `hg` (rename on either side, copy, rename with its own edit, divergent renames, rename against deletion). Directory renames are not followed: a file the other side added to a directory that was renamed away is reported as a conflict, where the original moves it to the new directory. Treemanifest repositories are refused. A file whose content hg4j has to merge is merged by line (`Merge3`); no external merge tool is run. Large files in LFS are written as their content, not as pointers. `setAllowAncestorMerge(true)` creates a merge the original refuses ("nothing to merge"); its tree is the tree of the descendant.

[source,java]
----
MergeCommitResult r = hg.mergeCommit()
    .setP1(receivingHead).setP2(sendingHead)
    .setUser("Name <mail@example.org>").setMessage("Merge pull request #12")
    .call();
if (r.isConflicted()) {
    show(r.getConflicts());
} else {
    publish(r.getNodeHex());
}
----

== Facade, hooks and exceptions

=== Hg (facade)

`Hg` is the porcelain entry point, similar to JGit's `Git`. It implements `AutoCloseable`. The javadoc states that instances are thread-safe for concurrent reads and writes, and that `runTransaction` gives thread and process atomicity for a sequence of operations (for example status followed by commit). Each command factory returns a fresh, unconfigured command object bound to the repository.

|===
|Method |Meaning

|`static Hg open(String path)` / `static Hg open(File directory)` |Opens an existing repository. Checks the requirements in both `.hg/requires` and `.hg/store/requires` against the supported list. Throws `IOException` when the repository is not found or invalid (`HgRepositoryNotFoundException` when `.hg` is missing).
|`static Hg wrap(HgRepository)` |Wraps an existing repository handle. A null raises `IllegalArgumentException`.
|`static InitCommand init()` |Command to initialize a repository.
|`static CloneCommand cloneRepository()` |Command to clone a repository.
|`static NarrowCloneCommand narrowClone()` |Command to make a narrow clone with a narrowed set of paths. Not tied to an existing repository.

|`List<HgHook> getHooks(HgHookType)` |The hooks registered for a phase.
|`void runTransaction(Runnable) throws Exception` |Runs the action while holding `lockWorkingCopy()` then `lockStore()` (exclusive, so no concurrent writer gets in between), and releases both when it ends. Lock failures and anything the action throws propagate.

=== HgHook and HgHookType

`HgHook` is a `@FunctionalInterface`: `boolean run(Map<String, Object> context) throws IOException`. Returning true allows the operation; returning false blocks it and aborts the transaction by raising an exception. It may throw `IOException` for an I/O error or a failed hook. The javadoc lists example context keys `author`, `message`, `commitNode`, `repository`; the keys actually passed differ by command. In `CommitCommand` the pre-commit context contains `author`, `message` and `repository`, and a false result throws `HgValidationException("Pre-commit hook execution rejected the commit txn")`.

The hooks that the wire servers and `HgLocalClient.pushWithHooks` run on the server side get these context keys (always `repository`, the changed `HgRepository`). The changegroup hooks (`prechangegroup`, `pretxnchangegroup`, `changegroup`) get `nodes`, a `List<String>` of 40-character hex node ids in the order they are applied; the first and last node and the count are read from the list. `pretxnchangegroup` and `changegroup` run only if at least one changeset is new to the repository, as in the original, and list the new changesets only; `prechangegroup` lists every changeset of the bundle. The `changegroup` hook runs after the locks are released and its result is ignored. The pushkey hooks (`prepushkey`, `pushkey`) get `namespace` (for example `bookmarks`), `key` (the name), `old` and `new` (hex node ids; the empty string, never `null`, for a bookmark that is created or deleted); the post hook runs only after a successful update. A refusal by a pre-hook is the answer `0` to a `pushkey` command and `prepushkey hook failed` inside a bundle2 push. `HgSshWireServer` and `HgHttpWireServer` support the same hooks.

Context keys and failure behavior of the other commands, from their javadoc and code: `PushCommand` passes `destinationUrl` and `repository` to pre hooks (false gives `HgValidationException`) and `destinationUrl`, `response` and `repository` to post hooks (return value ignored, exceptions swallowed, run after the locks are released, only after changesets were pushed). `RebaseCommand` passes `repository`, `sourceNode` and `targetNode` to pre hooks (false gives `HgValidationException`, message `Rebase rejected by PRE_REBASE hook`) and `sourceNode`, `targetNode`, `rebasedTipNode` (hex of the last new changeset, or null) and `repository` to post hooks (return value ignored, exceptions logged and swallowed). `GraftCommand` passes `sourceRevision`, `graftedNode` and `repository` to post hooks (return value ignored, exceptions logged as a warning, so a post-graft hook cannot abort the graft). `TagCommand` passes `repository`, `tag` and `node`; a pre hook returning false gives `HgValidationException` (`Tag creation rejected by PRE_TAG hook`), and exceptions from post hooks propagate.

Register with `hg.registerHook(HgHookType.PRE_COMMIT, ctx -> ...)`; the hook is attached to a command when it is created through the `Hg` factory method for that command. A command built with `new XCommand(repo)` does not receive the registered hooks. `ProcessHook` (class in the same package) is an `HgHook` that runs an external process and maps context entries to environment variables named `HG_<KEY>`. The command line is split on unquoted whitespace (single or double quotes group words; no shell is involved, so there is no expansion or redirection). Constructors take a command string, or a list with an optional working directory; without one the directory of the `repository` context entry is used, then the current directory of the JVM. A null, blank or empty command is accepted without running anything. Exit code 0 allows the operation; any other exit code logs a warning and rejects it (returns false).

=== Exceptions (package io.github.search5.hg4j.errors)

[cols="2,5"]
|===
|Class and parent |When thrown (from the javadoc and code), and what the caller should do

|`HgException` extends `Exception`
|Checked base class for Mercurial domain and operational exceptions (a constructor takes a message and optionally a cause). Not thrown by itself. Catch it only to handle `HgLockException` and `HgMergeConflictException` together.

|`HgLockException` extends `HgException`
|A repository lock cannot be acquired, or lock contention occurs (also when releasing the lock fails). The message is `Failed to acquire lock '<name>': ...`; `getLockName()` gives the lock name (for example `store.lock`, `wlock`). Commands that wait use the repository's push lock timeout; `0` fails at once. Caller action: retry later, or find and stop the other process. Do not delete lock files unless nothing else is running (`ChainsawUpdateCommand` breaks them on purpose).

|`HgAbandonedTransactionException` extends `HgLockException`
|An interrupted transaction (`store/journal`) is waiting: message `abandoned transaction found`, hint `run 'hg recover' to clean up transaction`, lock name `lock`. Thrown by `HgRepository.lockStore(int)` when a journal exists and the lock is not re-entrant. Nothing is recovered implicitly. Caller action: run `RecoverCommand` (`hg.recover().call()`), then retry. `lockStoreWithoutRecovery` does not raise it, which is why `VerifyCommand`, `RecoverCommand` and `GcCommand` use it.

|`HgMergeConflictException` extends `HgException`
|A 3-way merge left unresolved conflicts: `MergeCommand`, the cherry-pick path of `RebaseCommand` (also `ShelveCommand` unshelve), `GraftCommand` and `BackoutCommand`. `getConflictPath()` is the first conflicting file and `getConflictPaths()` all of them. Conflict markers are in the working files and the bookkeeping is in `.hg/merge/state2`. Caller action: resolve the files (for example with `ResolveCommand`), then continue (`continueRebase()`, `continueGraft()`, `unshelveContinue()`) or abort (`abort()`, `unshelveAbort()`); after a `BackoutCommand` conflict nothing is committed, so resolve and commit normally.

|`HgValidationException` extends `IOException`
|A precondition or integrity check on repository state or the working directory failed. This is the general "refused" signal of the commands, for example `uncommitted changes`, `outstanding uncommitted merge`, `no rebase in progress`, `empty revision set`, an unsupported option, or a hook that returned false. Caller action: read the message, fix the state (commit or revert changes, resolve the merge, correct the argument), and call again. Nothing has been changed when it is raised before the work starts.

|`HgPushRacedException` extends `HgValidationException`
|Server-side push/unbundle apply (local `file://` peer and bundle2 push): the repository heads, or a bookmark or phase, changed between the client's computation and the moment the store lock was taken, so the push lost a concurrent race. The message is `remote repository changed while pushing - please try again` (with details for bookmarks and phases). Nothing was applied. Caller action: catch it by type, pull the new changes, and retry the push.

|`HgCorruptDataException` extends `IOException`
|Data integrity failure: a revlog checksum mismatch, a corrupted delta restoration or index, or unreadable dirstate, sidedata, obsolescence or LFS pointer data. `UnbundleCommand` also raises it for an unknown bundle header or unsupported bundle1 compression. Caller action: do not retry blindly. Run `VerifyCommand`, restore from a backup or clone again; for an interrupted write, run `RecoverCommand`.

|`HgCensoredContentException` extends `IOException`
|Reading the content of a censored file revision through `Revlog` (mirrors `error.CensoredNodeError`) instead of silently returning the tombstone. `getTombstone()` returns the tombstone bytes (may be null). Caller action: treat the content as deliberately removed; use the tombstone text, or `getRawRevisionContent` on the revlog if the raw bytes are really wanted.

|`HgHookRejectedException` extends `IOException`
|A hook refused the operation. Raised by the local peer apply for a failing `pretxnchangegroup` hook (message `pretxnchangegroup hook failed`) and turned into a rejection reply by the server code. `isRolledBack()` is true when the hook ran after the changes were made and they were undone, false when it refused before anything changed. Caller action: the repository is back in its previous state when `isRolledBack()` is true; fix what the hook complained about and retry.

|`HgRepositoryNotFoundException` extends `IOException`
|A repository (or a required file such as a shelf or a filelog) cannot be found because of an invalid path or corruption; `getPath()` gives the path. Raised by `Hg.open`, `InitCommand` (a repository directory cannot be created), `ShelveCommand` for a missing shelf file and `CensorCommand` for a file with no filelog. Caller action: check the path and that `.hg` exists, or create the repository with `Hg.init()`.

|`HgRevisionNotFoundException` extends `IOException`
|A revision is not found by node id or revision number (the message names the 40-hex node or the revision number). Raised by commands that resolve revisions (for example `CensorCommand`, `SigCheckCommand`, `TreeMergeCommand`, `SignCommand`). Caller action: check the identifier; the changeset may be in another repository, stripped, or not pulled yet.

|`HgTransportException` extends `IOException`
|Base of network and wire protocol errors in the HTTP/SSH transport layer; the message is `Transport error for '<url>': ...` and `getRemoteUrl()` gives the URL. `HgRemoteClient` raises it itself for a malformed URL. Caller action: check the address and network; catch the base class to handle all transport failures.

|`HgAuthException` extends `HgTransportException`
|SSH or HTTP credential authentication failure: an HTTP 401 or 403 answer (the user name is `anonymous` when none was given), or an SSH authentication failure. `getUsername()` gives the user name that failed. Caller action: supply correct credentials (address, `[auth]` section, or `setCredentialsProvider` on `PullCommand`/`FetchCommand`) and retry.

|`HgProtocolException` extends `HgTransportException`
|Wire protocol error: capability negotiation fails, the server answers something the protocol does not allow, or a clone bundle download gets a non-200 response (`ClonebundlesCommand`). Caller action: check that the server supports the protocol version and capabilities in use (for example the SSH v2 switch), and that the URL points to a Mercurial server; retrying the same request will usually fail the same way.
|===

Note: `HgException` and `HgLockException` are checked exceptions that do not extend `IOException`; most others extend `IOException`.
