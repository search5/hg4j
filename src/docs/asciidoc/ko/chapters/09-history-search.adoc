[[history-search]]
== 히스토리 검색 및 탐색 (Searching & Browsing History)

이 장에서 다루는 커맨드는 파일 히스토리와 저장소 콘텐츠를 조회하는 `annotate()`, `cat()`,
`files()`, `locate()`, `manifest()`, `tree()`, `grep()`, `revset()`, `phase()`입니다. 이 가운데
`cat()`, `files()`, `locate()`, `manifest()`, `phase()`에 넘기는 리비전 문자열로는 리비전 번호와
hex 노드 프리픽스, `"tip"`만 쓸 수 있습니다. 북마크나 브랜치 이름은 직접 넘기지 못하니, 필요하면
`bookmark().call()` 등으로 노드 hex를 먼저 구해서 그 값을 넘기세요.

=== 파일 히스토리 blame(annotate)

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=annotate-file]
----

`annotate()`는 이름 변경(rename)과 복사(copy) 경계를 항상 따라갑니다. 실제 hg의 `hg annotate`도
마찬가지여서, 이를 켜는 `--follow` 플래그가 따로 없고 기본 동작이 곧 그렇습니다. 여기서
`setRevision(int)`에 넘기는 값은 체인지로그 리비전이 아니라 **해당 파일의 filelog 리비전 번호**
입니다(기본값 `-1`은 그 파일의 최신 filelog 리비전입니다). 반대로 결과로 돌아오는
`BlameLine#getRevision()`은 그 줄이 처음 들어온 **체인지로그 리비전 번호**(linkRev)입니다.
입력과 출력의 "리비전"이 서로 다른 종류이니 헷갈리지 마세요.

=== 추적 중인 파일 목록 조회하기

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=list-files]
----

`files()`는 `hg files`와 마찬가지로, 리비전을 지정하지 않으면 **작업 디렉터리**의 dirstate를
기준으로 동작합니다. 그래서 아직 커밋되지 않은 추가(added) 파일은 결과에 들어오고, `hg rm`으로
삭제 표시만 해 두고 커밋하지 않은 파일은 빠집니다. 리비전을 지정하면 그 커밋 시점의 매니페스트를
그대로 나열합니다. `setPattern(...)`으로는 글롭 패턴을 걸어 범위를 좁힐 수 있는데, 디렉터리를
가리키는 패턴은 그 아래 모든 파일에 매치되는 `SparsePathFilter`의 디렉터리-프리픽스 규칙을
따릅니다.

=== 패턴으로 파일 찾기 (locate)

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=locate-files]
----

`locate()`는 `files()`와 별개인, 더 오래된 커맨드입니다. 리비전을 지정하지 않으면 dirstate를
**직접** 뒤지기 때문에 `hg rm`으로 삭제 표시만 되고 아직 커밋되지 않은 파일까지 결과에
들어옵니다. `files()`와 가장 크게 갈리는 지점이 바로 여기입니다. 패턴을 지정하지 않으면 후보
경로가 전부 나오고, 기본 패턴 종류는 실제 hg와 같은 `relglob`(경로의 어느 디렉터리에서든 파일명
부분에 매치되는, 루트에 고정되지 않은 글롭)입니다. 지원하는 와일드카드는 `*`, `**`, `?`뿐이고,
`[...]` 문자 클래스나 `{a,b}` 중괄호 확장은 리터럴 문자로 취급합니다.

=== 매니페스트 목록 조회하기

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=list-manifest]
----

`manifest()`는 리비전을 지정하지 않으면 tip이 아니라 **작업 디렉터리의 첫 번째 부모**를 기준으로
동작합니다. 예를 들어 `hg update -r 0`으로 이전 리비전을 체크아웃한 뒤 리비전 없이 호출하면
tip이 아니라 리비전 0의 파일 목록이 나옵니다. 돌아오는 `ManifestEntry`에는 파일 경로와 콘텐츠의
40자리 hex 노드 ID 전체, 실행 가능 여부, 심볼릭 링크 여부가 담깁니다. `setDebug(boolean)`은
호출자가 어떤 렌더링을 의도했는지 적어 두는 용도일 뿐, `call()`이 반환하는 데이터에는 아무 영향이
없습니다. 렌더링에 필요한 정보(노드 hex 포함)는 어차피 항상 전부 실려 옵니다.

`tree()`는 리비전을 지정하지 않으면(또는 지정한 리비전이 해석되지 않으면) tip을 기준으로

`TreeEntry#getMode()`는 POSIX 스타일 모드(일반 파일 `0644`, 실행 파일 `0755`, 심볼릭 링크
`0120000`)를 돌려줍니다.

=== 히스토리 전체에서 문자열 검색하기 (grep)

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=grep-history]
----

`grep()`이 뒤지는 범위는 작업 디렉터리나 리비전 하나가 아니라 추적 중인 **모든 파일의 모든
filelog 리비전**입니다. 같은 줄이 여러 리비전에 그대로 남아 있으면 그 횟수만큼 결과에 거듭 나올
수 있습니다. `setQuery(...)`는 일반 문자열은 물론 정규식도 그대로 받는데, 실제 `hg grep`의 기본
동작과 같습니다. `GrepResult`의 `path`, `hexNode`, `lineNumber`, `lineContent`는 getter가 아니라
`public final` 필드라서 바로 꺼내 쓰면 됩니다.

조회에 그치지 않고 phase를 바꿉니다.

[source,java]
----
include::{examplesdir}/HistorySearchExamples.java[tag=set-phase]
----

phase를 더 낮은(더 public에 가까운) 값으로 내리는 일은 언제나 허용되고, 대상 리비전의 **모든
조상**에도 함께 적용됩니다. 자식이 부모보다 덜 public할 수는 없기 때문입니다. 반대로 더 높은(더
secret에 가까운) 값으로 올리면 대상 리비전의 **모든 자손**에 적용되는데, 실제 hg의
`hg phase --force`와 마찬가지로 `setForce(true)`를 명시하지 않으면 `IOException`으로 거부됩니다.
