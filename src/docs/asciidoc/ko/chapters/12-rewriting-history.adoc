[[rewriting-history]]
== 히스토리 재작성 (Rewriting History)

이 장에서 다루는 커맨드는 저마다 "재작성"의 방식이 전혀 다릅니다. `amend()`와 `histedit()`는
4장의 `rebase()`와 마찬가지로 원본 리비전을 물리적으로 지우지 않고 obsolescence marker만
기록해 대체합니다. 반면 `graft()`는 원본을 건드리지 않고 그 변경사항을 복사한
새 커밋을 만들 뿐이며, `backout()`은 아예 새로운 "되돌리기" 커밋을 추가할 뿐 히스토리 자체는
그대로 둡니다. `treeMerge()`/`mergeCommit()`은 이 둘과도 성격이 다른, 작업 디렉터리를
전혀 거치지 않는 순수 계산/기록 커맨드입니다. 각 절에서 이 차이를 구체적으로 짚습니다.

`amend()`는 tip 커밋을 대체하는 새 커밋을 만듭니다. 이때 새 커밋은 amend 대상이 된
원래 커밋의 **자식이 아니라, 같은 부모를 공유하는 형제**로 생깁니다(실제 `hg commit
--amend`와 동일). `setAuthor()`/`setMessage()`/`setCloseBranch()`를 호출하지 않으면 원래
커밋 자신의 값을 그대로 재사용합니다. 완료 후에는 원본 커밋에서 새 커밋으로 이어지는
obsolescence marker를 `.hg/store/obsstore`에 기록하므로, 원본은 `hg log --hidden`으로만
보입니다.

[source,java]
----
include::{examplesdir}/HistoryRewriteExamples.java[tag=histedit-rules]
----

`histedit()`는 리비전 하나하나에 규칙(`Rule`)을 붙여 순서대로 재생하는 방식입니다.
`addRule(Action, hexNode)`로 쌓은 규칙 목록은 **가장 오래된 리비전부터** 순서대로
나열해야 하며(대화형 리베이스의 "할 일 목록"과 같은 개념), 재작성 범위는 항상 첫 번째
규칙이 가리키는 리비전의 부모부터 시작하는 연속된 구간입니다.

각 `Action`의 의미는 다음과 같습니다.

* `PICK` -- 해당 리비전을 그대로 재커밋합니다(기본 동작).
* `FOLD` -- 해당 리비전의 변경사항과 커밋 메시지를 **직전 PICK/FOLD/ROLL 그룹에 합칩니다**
  (메시지는 뒤에 이어 붙습니다).
* `ROLL` -- `FOLD`와 같지만 커밋 메시지는 버립니다.
* `DROP` -- 해당 리비전을 완전히 버립니다. 물리적으로 스트립하지는 않고, `prune`
  obsolescence marker를 기록해 평범한 `hg log`에서 보이지 않게만 만듭니다.

`DROP`한 리비전이 추가했던 파일은 histedit이 끝나면 작업 디렉터리에서도 함께 사라지고,
dirstate도 새 tip 기준으로 재조정됩니다. 실제 `hg histedit`이 끝난 뒤 암묵적으로 새
tip을 체크아웃하는 것과 같습니다.

`graft()`는 Git의 cherry-pick에 해당합니다. 지정한 소스 리비전의 변경사항을 현재 작업
디렉터리의 부모 위에 새 커밋으로 복사합니다. `amend()`/`histedit()`와 달리 obsolescence
marker는 **전혀 남기지 않습니다**. 실제 `hg graft`와 마찬가지로 graft는 재작성이 아니라
복사이므로, 소스 리비전은 이식 이후에도 평범한 `hg log`에 그대로 보입니다.

목적지와 소스가 같은 파일을 서로 다르게 변경해 두었다면 실제 3-way 병합이 일어나며,
저절로 정리되지 않는 충돌이 남으면 `HgMergeConflictException`을 던집니다(복구 방법은
<<error-handling>> 참고). graft는 rebase와 달리 자체적인 일시정지/재개 상태를
갖습니다.

작업 디렉터리를 graft 이전 상태로 되돌립니다. 이 일시정지 상태는 hg4j 자체 포맷이라
실제 `hg graft --continue`/`--abort`와 중간 상태까지 상호운용되지는 않습니다. 다만 결과로
남는 커밋과 충돌 마커 형식 자체는 실제 hg와 호환됩니다.

=== 커밋 되돌리기 (backout)

[source,java]
----
include::{examplesdir}/HistoryRewriteExamples.java[tag=backout-revision]
----

`backout()`은 지정한 리비전의 변경사항을 취소하는 **새 커밋**을 추가할 뿐, 히스토리
자체는 그대로 둡니다(obsolescence marker도, 스트립도 없습니다). 병합 커밋은
지원하지 않으며(부모가 둘인 리비전을 대상으로 지정하면 예외가 발생합니다), 결과 커밋은
항상 부모가 하나인 선형 히스토리를 유지합니다.

두 가지 경우로 나뉩니다.

* 대상 리비전이 **작업 디렉터리의 현재 부모 자신**인 경우(가장 흔한 경우) -- 작업 디렉터리가
  이미 그 리비전과 정확히 일치하므로, 그 리비전과 자신의 부모 사이의 diff를 그대로 적용하면
  되고 충돌이 날 수 없습니다.
* 대상 리비전이 그보다 오래된 조상인 경우 -- ancestor를 대상 리비전 자신, local을 현재
  작업 디렉터리, other를 대상 리비전의 부모로 삼아 실제 3-way 병합을 수행합니다. 이 방식
  덕분에 대상 리비전 이후에 생긴 무관한 변경사항은 그대로 유지되면서 대상 리비전의 효과만
  취소됩니다.

두 번째 경우에서 진짜 충돌이 나면 `HgMergeConflictException`을 던지고 커밋도 만들지
않습니다(<<error-handling>> 참고). 다만 `graft()`/`rebase()`와 달리 `backout`에는
"이어서 계속하기"에 해당하는 메서드가 없습니다. 충돌 파일을 직접 해결한 다음에는
`backout()`을 다시 부르지 말고 그냥 평범하게 `commit()`을 호출하면 됩니다.

=== 작업 디렉터리 없이 병합 계산·기록하기 (treeMerge, mergeCommit)

[source,java]
----
include::{examplesdir}/HistoryRewriteExamples.java[tag=tree-merge-and-commit]
----

`merge()`(4장)는 작업 디렉터리를 실제로 갱신하는 포셀린 커맨드이고, 충돌은 예외가 아니라
`MergeResult.isConflicted()`로 보고합니다. `treeMerge()`는 이와 정반대로 **작업 디렉터리와
dirstate를 전혀 건드리지 않고**, changelog/manifest/filelog 저장소만 읽어 병합 결과를
순수한 데이터(`TreeMergeResult`)로 계산합니다. 바뀌거나 추가해야 할 파일(`getChangedFiles()`),
지워야 할 파일(`getRemovedFiles()`), 충돌 여부(`isConflicted()`/`getConflicts()`) 같은 값을
그대로 반환할 뿐, 아무것도 디스크에 쓰지 않습니다.

`mergeCommit()`은 그 계산 결과(`TreeMergeResult`)를 실제 부모가 둘인 새 체인지셋으로
changelog/manifest/filelog에 직접 기록합니다. 이때도 작업 디렉터리는 손대지
않습니다. 충돌이 있는 `TreeMergeResult`는 거부하므로 반드시 `isConflicted()`가
`false`인 결과만 넘겨야 합니다. 북마크는 자동으로 옮겨지지 않으니, 필요하다면 반환된
노드로 직접 `bookmark()` 커맨드를 호출하십시오.

이 조합은 저장소 전체를 임시 디렉터리에 클론하고 체크아웃한 뒤 `merge()` + `commit()`을
돌리고 결과만 다시 push하는 방식보다 훨씬 저렴합니다. 비용이 병합에서 실제로 건드리는 파일
수에만 비례하기 때문입니다. 서버 사이드 병합이나, 체크아웃 없이 PR 병합 결과를 미리
계산해 보는 용도에 적합합니다.
